# interfaces-dependency-injection

## 目标

通过一个课程预约服务理解接口和依赖注入的基本思想。这个例子不引入 ASP.NET Core 的依赖注入容器，而是用标准库和构造函数参数展示最核心的设计：业务类依赖抽象能力，而不是在内部直接创建具体实现。

真实工程里，发送通知、读取时间、访问数据库、调用外部 API 都是会变化、会失败、需要替换的边界。如果 `LessonScheduler` 在方法里直接 `new ConsoleNotifier()` 或直接读取 `DateTimeOffset.Now`，测试就很难稳定，未来换成邮件、短信或假时钟也会牵动业务代码。

## 特性说明

`IClock` 表示“能提供当前时间”的能力，`INotifier` 表示“能发送消息”的能力。`LessonScheduler` 通过主构造函数接收这两个接口，只关心能力，不关心实现。程序入口把 `FixedClock` 和 `ConsoleNotifier` 组合起来，这就是最小形式的依赖注入。

接口是 C# 面向对象模型里非常重要的契约工具。它不保存业务状态，只描述调用方可以使用哪些成员。类通过实现接口承诺自己具备某种能力；消费方以接口为参数，就可以接收任意实现。这个边界让测试替身、框架适配器和生产实现可以共用同一业务类。

如果不用接口和注入，常见退化是业务对象自己创建所有依赖：读取系统时间、打开文件、发网络请求、写控制台都混在一个方法里。这样的代码能跑，但很难替换、很难测试，也很难在失败时隔离责任。

## 设计取舍

接口会增加一点间接层。对于非常稳定、没有替换需求的纯计算辅助函数，过早抽接口可能让代码显得臃肿。这里选择时间和通知作为接口，是因为它们天然位于系统边界：时间会让测试不稳定，通知会连接外部世界。

依赖注入容器能自动创建对象图、管理生命周期和配置实现，但容器不是思想本身。先理解“从外部传入依赖”，再学习 ASP.NET Core 的 `IServiceCollection` 会更容易。这个例子手动组装对象，是为了让你看见容器背后真正发生的事。

接口也不等于插件系统。接口设计得太宽，调用方仍会被实现细节拖住；设计得太碎，又会制造过多文件和样板。好的接口通常围绕调用者需要的能力命名，而不是照着某个具体类机械抽取。

## 运行

```bash
cd languages/csharp-dotnet/features/examples/interfaces-dependency-injection && dotnet run
```

## 观察点

- 输出时间基于 `FixedClock`，所以每次运行结果稳定，不受真实系统时间影响。
- `LessonScheduler` 没有直接引用 `ConsoleNotifier`，只调用 `INotifier.Send`。
- `Schedule` 方法的业务逻辑只负责计算开始时间和组织消息，边界行为交给依赖对象。
- 把 `ConsoleNotifier` 换成另一个实现时，`LessonScheduler` 不需要修改。
- 这个例子展示的是依赖注入思想，不是某个框架容器的配置语法。

## 延伸练习

- 新增 `ListNotifier`，把消息保存到列表中而不是写控制台，模拟单元测试里的断言。
- 把 `FixedClock` 换成 `SystemClock`，由它返回 `DateTimeOffset.Now`，观察输出如何变成真实时间。
- 给 `LessonScheduler` 增加“延迟不能小于 1 小时”的校验，思考这是业务规则还是通知实现的责任。
