# Java

## 语言定位

Java 的第一版学习基线是 **25 LTS**，工具链入口是 **JDK 25**。它主要用于：企业服务、Android 生态、数据平台、中间件。

Java 的核心定位是“长期可维护的通用工程语言”。它把源代码编译成 JVM 字节码，再交给虚拟机执行，换来跨平台部署、成熟的运行时优化和强大的生态兼容性。Java 的设计哲学偏保守：语法更新通常会照顾旧代码，标准库和运行时也尽量保持稳定；这让它非常适合十年尺度的系统，但也意味着新特性往往以渐进方式进入语言。现代 Java 已经不只是传统面向对象语言，record、sealed class、模式匹配、局部变量类型推断、虚拟线程等特性，让它在数据建模、并发服务和领域表达上更轻量。

## 适合场景

- 需要理解该生态的工程化默认选择，例如包管理、构建、测试和发布。
- 需要横向比较不同语言在类型、并发和错误处理上的设计取舍。
- 需要从小案例过渡到代表性框架，而不是只背语法。

Java 适合企业后端、交易系统、数据处理平台、消息中间件、搜索与存储服务、Android 旧有生态，以及对稳定性、可观测性和团队协作要求高的项目。JVM 的 JIT、GC、线程模型和诊断工具经过多年打磨，适合跑常驻服务。它不太适合极小脚本、一次性命令行胶水、对启动时间和内存占用极端敏感的函数式任务，也不是写操作系统内核、驱动或裸机程序的首选。学习时要带着“工程语言”的眼光看 Java：语法只是入口，真正的价值在依赖管理、模块边界、运行时调优、日志监控和团队约定。

## 核心语法

重点学习变量/常量、函数、模块、数据结构、泛型或类型标注、控制流，以及该语言最常见的代码组织方式。案例会尽量保持短小，让语法特征直接暴露出来。

Java 代码通常以 package、class/interface/record、方法和字段组织。入口可以是传统 `public static void main(String[] args)`，新版本也在降低入门样板。变量分为基本类型和引用类型；`var` 只做局部变量类型推断，不能替代清晰的 API 类型。控制流包含 `if`、`switch`、循环、增强 for，现代 `switch` 可作为表达式使用。面向对象部分要掌握封装、接口、继承和组合，但更推荐优先用组合表达行为，用接口定义边界。

惯用法上，简单数据载体优先考虑 `record`，有限层级可用 `sealed`，集合处理可用 Stream，但不要为了“函数式感”牺牲可读性。`Optional` 适合表达返回值可能为空，不适合做字段或方法参数的万能包装。泛型常用于集合、仓储、转换器和服务边界；理解通配符 `? extends` / `? super` 能避免很多 API 设计困惑。

## 类型/内存/并发模型

- 类型模型：静态、名义类型、泛型擦除。
- 并发模型：线程、虚拟线程、结构化并发。
- 内存与资源：结合语言自己的生命周期管理方式学习，不把所有语言都套成同一种范式。

Java 是静态、名义类型语言：类型兼容主要由声明关系决定，而不是“长得像”。它同时有基本类型和引用类型，装箱/拆箱让二者能在集合和泛型中协作，但也会带来性能和空值问题。泛型在运行期采用类型擦除，这保证了历史兼容，却限制了某些运行时类型判断。

内存主要由 GC 管理，开发者通常不手动释放对象；但文件句柄、数据库连接、Socket 等外部资源必须显式关闭，首选 `try-with-resources`。并发方面，传统模型包括 `Thread`、`ExecutorService`、锁、并发集合和 `CompletableFuture`。JDK 25 时代还要重点理解虚拟线程：它让“一个请求一个线程”的阻塞式代码重新变得可伸缩，但并不消除共享状态、锁竞争、连接池容量和取消传播这些问题。学习并发时应同时理解 Java 内存模型、可见性、不可变对象和线程安全集合。

## 标准库与包管理

包管理入口：Maven / Gradle。第一版案例优先使用标准库，只有框架章节才引入生态依赖。

Java 标准库覆盖集合、并发、I/O、NIO、时间日期、正则、HTTP Client、日志接口、反射、序列化和安全等基础能力。`java.time` 应替代旧的 `Date` / `Calendar`；集合要熟悉 `List`、`Map`、`Set` 的接口与实现差异；I/O 任务要区分字节流、字符流、路径 API 和异步/非阻塞能力。Maven 强调约定和稳定生命周期，Gradle 更灵活、适合复杂构建。无论使用哪一个，都要理解坐标、作用域、依赖传递、锁定版本、测试任务和可重复构建。

## 错误处理

受检异常、运行时异常、try-with-resources。学习时关注错误如何被表达、传播、恢复，以及如何避免把异常路径藏在业务逻辑里。

Java 的异常体系分为受检异常、运行时异常和错误。受检异常强迫调用方处理或声明，适合 I/O、网络、解析这类可预期失败；运行时异常常表示编程错误或业务前置条件被破坏。不要吞掉异常，也不要把所有异常都包装成同一种 `RuntimeException`。在边界层可以把底层异常转换成领域错误，在服务内部则保留足够上下文。资源相关代码优先使用 `try-with-resources`，日志要记录操作对象和关键输入，但避免泄露敏感数据。

## 工程化

第一阶段关注代码格式、测试入口、依赖声明和可重复运行。大型工程主题，如性能分析、发布、观测和安全，会在框架章节逐步展开。

Java 工程化的学习路径建议是：先会用 JDK 编译运行单文件，再理解 Maven/Gradle 项目结构，然后补齐 JUnit 测试、断言、日志、配置和打包。之后再进入 Spring、Quarkus、Micronaut 等框架会更稳。真实项目中还需要关注代码格式、静态检查、依赖漏洞扫描、容器镜像、运行参数、GC 日志、线程 dump、heap dump 和指标采集。模块系统 `module-info.java` 值得了解，但许多企业项目仍以构建工具和包结构作为主要边界。

## 常见坑

- 只学习语法而忽略包管理和项目结构。
- 把其他语言的范式硬搬过来，错过本语言的惯用表达。
- 示例能跑但没有预期输出，导致无法判断自己是否真正理解。

常见问题还包括：把 `==` 用在字符串内容比较上；忽略 `equals` / `hashCode` 约定导致集合行为异常；过度使用继承造成层级僵硬；在 Stream 中塞入复杂副作用；把 `Optional.get()` 当成空值检查；在虚拟线程中继续使用过小连接池；捕获异常后只打印不处理；不了解时区导致时间计算错误。学习时每写一个案例都应补上输入、预期输出和失败路径。
