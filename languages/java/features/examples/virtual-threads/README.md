# virtual-threads

## 目标

这个例子展示 Java 虚拟线程如何让阻塞式任务保持顺序可读，同时并发等待多个慢操作。三个库存查询都用 `Thread.sleep` 模拟 I/O 等待；使用虚拟线程后，调用方仍然写普通方法和 `Future.get()`，但总耗时接近最慢的单个查询。

真实服务端代码经常在等待数据库、HTTP、消息队列或文件系统。过去如果为每个请求都占用一个平台线程，线程栈和调度成本会限制并发量；如果改成异步回调，业务流程又容易被拆得很碎。本例希望你观察：虚拟线程让“一个任务一段顺序代码”重新变得经济，尤其适合大量等待型工作。

## 特性说明

`Executors.newVirtualThreadPerTaskExecutor()` 会为每个提交的任务创建一个虚拟线程。虚拟线程由 JVM 调度，不是一对一绑定昂贵的操作系统线程；当任务阻塞等待时，JVM 可以释放承载线程去运行别的虚拟线程。例子中三个查询分别等待 650、400、550 毫秒，但它们并发开始，所以总耗时应接近最慢的 650 毫秒，而不是三者相加。

代码仍然使用同步写法：`fetchInventory` 是普通方法，`Thread.sleep` 模拟阻塞，调用方用 `Future.get()` 收集结果。这是虚拟线程的重要价值：降低等待成本，而不是强迫所有业务逻辑改成回调或反应式链。

如果不用虚拟线程，你可能会限制平台线程池大小，导致大量等待任务排队；或者把流程改写成 `CompletableFuture` 链，增加异常传播、取消和调试成本。对于 CPU 密集型任务，虚拟线程不会让 CPU 变多；它主要改善等待型并发。

## 设计取舍

Java 选择让虚拟线程兼容现有阻塞式 API，这保护了大量已有库和代码。代价是开发者仍必须理解资源边界：数据库连接池、HTTP 连接池、文件句柄、限流器和外部服务配额不会因为虚拟线程变多而自动扩容。

例子用 `try-with-resources` 包住 executor，强调任务生命周期。离开作用域时 executor 会关闭，调用方不会把后台任务悄悄遗留到程序结束之后。虚拟线程让并发写法更简单，但共享可变状态、锁竞争、超时、取消、背压和下游容量仍然需要设计。

## 运行

```bash
javac Main.java && java Main
```

## 观察点

- 输出会打印三个 `Inventory[...]`，说明每个阻塞任务都像普通函数一样返回结果。
- `elapsed millis` 应接近 650 毫秒再加少量调度开销，而不是约 1600 毫秒。这个现象验证了三个等待并发发生。
- `try-with-resources` 会关闭 executor，表达“这些任务属于这个作用域”。
- 如果把三个 `fetchInventory` 改成顺序调用，总耗时会接近所有延迟相加。

不要把这个结果理解成“虚拟线程越多越好”。如果每个任务都拿数据库连接，而连接池只有 20 个，1000 个虚拟线程仍会在连接池边界排队。虚拟线程降低线程等待成本，但不消除下游容量限制。

## 延伸练习

- 把任务数量扩展到 100 或 1000，观察代码结构是否仍保持顺序可读。
- 给 `future.get()` 外层增加超时控制，思考超时后应该如何取消还没完成的任务。
- 在任务中写入一个共享 `ArrayList`，再改用并发集合或只返回不可变结果，比较两种设计。
- 把 `Thread.sleep` 换成标准库 `HttpClient` 调用本地服务，观察真实 I/O 等待和示例中的模拟等待有什么相同边界。
