# Java 特性与思想辅助教学

## 如何使用

这个模块把 Java 的语言思想和可运行代码放在一起学习。建议先阅读本页的思想总览，再进入每个例子目录运行 `javac Main.java && java Main`，最后回到“学习检查”解释自己观察到的输出。三个例子都只使用 JDK 标准库，不依赖 Maven、Gradle 或第三方框架，目的是让注意力集中在语言特性本身。

学习 Java 时不要只背语法关键字。Java 的许多设计都服务于长期演进的大型工程：代码需要被不同团队维护，API 需要在多年后仍然兼容，运行时需要在不同平台上稳定工作。因此，本模块会持续追问三个问题：这个特性解决什么问题，Java 为什么用这种方式解决，代码运行时能观察到什么边界。

## 思想总览

Java 的核心思想可以概括为“用显式边界换长期可维护性”。类、接口、包、访问控制、异常声明、泛型、record 和 sealed class 都在帮助开发者把变化限制在可以理解的范围内。它不是追求最少字符的语言，而是倾向于让公共 API、失败路径和数据结构的含义可读、可审查、可演进。

面向对象在 Java 中不仅是“把数据和方法放进类”。更重要的是通过接口抽象行为边界，通过组合减少继承层级带来的僵硬，通过不可变值对象减少共享状态带来的并发风险。现代 Java 又补上了 record、sealed class、模式匹配、虚拟线程等能力，让传统工程语言也能更直接地表达数据、领域状态和高并发流程。

并发方面，Java 的思想也发生了变化。传统平台线程成本较高，开发者常被迫把简单业务拆成回调、Future 链或复杂线程池配置。虚拟线程让阻塞式代码重新具备伸缩性，但它不是“自动并行正确”。学习者仍要关注任务边界、取消、超时、共享状态、连接池容量和资源关闭。

异常和资源边界是 Java 工程味最重的部分。GC 管对象内存，但不替你关闭文件、Socket 或数据库连接。受检异常让部分失败成为方法签名的一部分，运行时异常表达调用约定被破坏或无法恢复的情况。好的 Java 代码会在边界处转换错误，在资源处明确关闭，在业务层保留足够上下文。

## 核心特性地图

1. 面向对象与接口抽象

   它解决的问题是：业务变化时，调用方不应该依赖某个具体实现的所有细节。Java 用名义类型、接口和类来表达这种边界，因为大型工程中“谁承诺了什么行为”比“对象刚好有哪些方法”更重要。接口适合定义能力，例如支付、通知、仓储、策略；类或 record 负责承载具体状态。学习者可以在 `sealed-domain-result` 例子中观察接口、sealed class 和业务处理函数如何分工。

2. record 与 value modeling

   它解决的问题是：大量数据载体如果都手写构造器、访问器、`equals`、`hashCode` 和 `toString`，既啰嗦又容易出错。Java 用 `record` 明确声明“这个类型主要是值”，自动生成基于组成字段的相等性和只读访问器。这种方式符合 Java 的兼容思路：它没有取消 class，而是为值建模提供更窄、更清晰的语法。学习者应该运行 `records-value-modeling`，观察两个字段相同的订单行为什么相等，以及紧凑构造器如何保护不变量。

3. sealed class 与领域建模

   它解决的问题是：很多领域状态是有限集合，例如支付结果只能是成功、拒绝、待审核或系统失败。如果使用普通继承，未来任何类都可能扩展这个层级，处理逻辑难以判断是否覆盖完整。Java 用 `sealed interface` / `sealed class` 加 `permits` 限定可实现类型，让“这个领域结果只有这些形态”写进类型系统。学习者应该运行 `sealed-domain-result`，观察 `switch` 或分支处理如何围绕有限结果集合组织。

4. 虚拟线程与并发结构化思维

   它解决的问题是：服务端常见任务会等待网络、文件或数据库，平台线程在等待时占用昂贵资源。Java 用 JVM 调度的虚拟线程降低阻塞等待成本，让“一项业务一个顺序任务”的写法重新可行。它选择兼容现有阻塞式 API，而不是要求所有代码改成异步回调。学习者应该运行 `virtual-threads`，观察多个任务同时休眠时总耗时接近最慢任务，而不是所有任务时长之和；同时注意例子仍然用超时和关闭 executor 表达任务边界。

5. 异常和资源边界

   它解决的问题是：失败和资源泄漏经常发生在系统边界，例如读文件、调用网络、解析输入。Java 用异常体系表达失败传播，用 `try-with-resources` 保证实现 `AutoCloseable` 的资源在离开作用域时关闭。受检异常让调用方看见可预期失败，运行时异常保留给违反约定或难以恢复的问题。学习者可以先看根目录的 `examples/errors`，再在 `virtual-threads` 中观察并发任务如何把失败汇总到调用方。

## 深入理解与对比练习

### 从“类很多”到“边界清楚”

Java 初学者常把面向对象理解成“为每个名词建一个类”，于是很快得到一堆只包字段、不承载规则的贫血对象。更好的观察方式是：类和接口应该在变化点上形成边界。比如支付渠道会变化，就抽象成接口；订单行只是值，就用 `record`；支付结果是有限集合，就用 sealed hierarchy。运行例子后可以尝试把一个 `Map<String, Object>` 版本的订单改成 `record`，观察字段名、构造校验和 `equals` 如何减少隐式约定。

### 值对象不是“更短的 class”

`record` 的重点不是省代码，而是把“身份不重要，组成字段才重要”的语义写进类型。适合 `record` 的对象通常不可变、可比较、可作为 Map key 或事件载荷；不适合的对象通常有生命周期、可变内部状态、懒加载资源或继承层级。学习 `records-value-modeling` 时，建议故意传入负数金额，看构造阶段如何阻止坏数据进入系统；再把 `record` 改成普通 class，体会你需要手写哪些行为才能保持同样语义。

### sealed 类型让分支有终点

业务代码里最常见的隐患之一是字符串状态码。`"SUCCESS"`、`"success"`、`"OK"` 很容易在不同模块漂移。sealed 类型的价值是让状态集合在编译期可见，处理逻辑也能围绕有限分支展开。学习 `sealed-domain-result` 时，可以新增一个 `PendingReview` 结果类型，然后观察哪些处理函数必须补分支。这种“新增状态会推动调用方更新”的反馈，正是类型系统帮助维护业务完整性的地方。

### 虚拟线程降低等待成本，不消除共享状态问题

虚拟线程让阻塞式代码重新变得经济，但它不是并发正确性的万能药。数据库连接池、限流器、文件句柄和外部 API 配额仍然是稀缺资源；共享 `ArrayList` 或可变对象仍然可能产生竞态。学习 `virtual-threads` 时，可以把任务数增加到 1000，观察代码结构是否仍然简单；再加入一个共享计数器，思考为什么还需要同步、不可变数据或并发集合。

### 错误边界要贴近系统边界

Java 代码不应该把所有异常都直接抛到最外层，也不应该在底层吞掉上下文。更好的做法是在系统边界保留技术细节，在领域边界转换成业务可理解的错误。比如文件读取失败是 `IOException`，但订单导入失败可能需要携带行号、订单号和原因。阅读例子时，尝试给每个失败路径补一句上下文信息，并说明这条信息应该暴露给用户、日志还是调用方。

## 教学例子索引

- [records-value-modeling](examples/records-value-modeling/)：用 `record` 表达订单行、金额和订单汇总，观察值相等、不变量和不可变数据组合。
- [sealed-domain-result](examples/sealed-domain-result/)：用 sealed interface 表达有限业务结果，观察领域状态如何比字符串状态码更可维护。
- [virtual-threads](examples/virtual-threads/)：用虚拟线程执行多个阻塞式任务，观察并发等待、任务收集和资源关闭。

## 学习检查

- 你能解释为什么 `record` 更适合值对象，而不是所有类都改成 record 吗？
- 你能指出接口抽象和继承复用的区别，并说出什么时候应该优先组合吗？
- 你能把一个“字符串状态码 + if/else”的结果模型改写成 sealed 类型层级吗？
- 你能解释虚拟线程降低了什么成本，又没有替你解决哪些并发问题吗？
- 你能说明 GC 管理对象内存和 `try-with-resources` 管理外部资源之间的边界吗？
- 你能为每个例子增加一个失败输入，并预测 Java 会在构造、分支还是任务收集阶段暴露错误吗？
