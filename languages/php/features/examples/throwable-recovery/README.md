# throwable-recovery

## 目标

模拟一次请求处理：业务异常可以转换为可读响应，类型错误代表程序缺陷，`finally` 保证清理逻辑执行。理解 `Throwable` 是 `Exception` 与 `Error` 的共同边界，并练习在应用边界统一记录、恢复或失败。

## 特性说明

PHP 7 以后，`Exception` 和 `Error` 都实现 `Throwable`。这让框架或入口文件可以用一个顶层边界捕获大多数失败，统一转换为 HTTP 响应、日志或命令行退出码。例子用命令行模拟请求：业务函数可能抛出可恢复异常，也可能因为类型错误暴露程序缺陷。

`finally` 表达的是“无论成功还是失败都要做”的清理承诺。真实项目里它可能对应关闭临时文件、释放锁、回滚事务或记录请求完成日志。注意：能捕获 `Throwable` 不代表应该吞掉所有错误；顶层边界应该决定如何报告，而不是让错误静默消失。

## 设计取舍

把所有函数都返回数组状态码会让正常路径充满 `if (!$ok)`，而异常能让失败从深层传播到边界集中处理。代价是异常路径不如返回值直观，需要团队约定哪些异常可恢复、哪些代表程序 bug。

这个例子把业务异常和类型错误分开展示：业务异常可以转换为用户可理解的响应；类型错误通常应该被记录并修复。统一捕获边界适合放在入口或框架层，不适合散落在每个小函数里。

## 运行

```bash
php main.php
```

## 观察点

- 成功请求、业务失败和程序错误会走不同输出路径。
- `DomainException` 可以转成业务响应，因为调用方知道如何恢复。
- `TypeError` 虽然也能被捕获，但更像代码缺陷，应该记录并修复。
- `finally` 输出说明清理逻辑不依赖前面是否抛异常。

## 延伸练习

- 增加一个 `InvalidArgumentException`，表示外部输入缺字段，并把它转换成 400 类响应。
- 在 `finally` 中模拟释放锁或关闭临时文件，观察所有路径都会执行。
- 把异常改成返回 `['ok' => false]` 的数组，比较调用方代码是否更啰嗦。
