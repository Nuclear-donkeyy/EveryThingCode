# readonly-objects

## 目标

用 `readonly` 属性构建不可变配置对象，理解现代 PHP 如何表达“创建后不再改变”的值。这个例子展示配置、请求参数、命令对象这类数据为什么适合不可变模型。

## 特性说明

`readonly` 属性只能在初始化阶段写入，之后不能再次赋值。它解决的是对象在多个函数之间传递时被意外修改的问题。对于配置、金额、ID、时间范围这类值，调用方通常希望拿到的是稳定快照，而不是一个可能被任意服务改掉的可变容器。

不可变对象还让测试和日志更可靠：一旦构造成功，后续输出就能代表当时的输入状态。例子中的 `ReportOptions` 保存报表日期范围和格式，构造器负责校验，业务函数只负责读取。

## 设计取舍

不可变对象会让“修改”变成“创建新对象”。这多了一步构造，但换来了更容易推理的状态变化。如果对象代表数据库连接、缓存客户端或累积统计器，它就不适合 readonly 值对象；如果对象代表一次请求的参数或领域值，readonly 往往更稳。

PHP 的 `readonly` 不会自动做深层不可变：如果 readonly 属性指向一个可变对象，那个对象内部仍可能改变。因此，设计值对象时还要关注属性类型本身是否可变。

## 运行

```bash
php main.php
```

## 观察点

- 合法的 `ReportOptions` 会被传入函数并生成报表描述。
- 尝试修改 readonly 属性会触发 `Error`，说明对象状态被语言保护。
- 构造器仍然负责日期范围和格式的领域校验。
- 不可变对象适合传递配置，不适合承载长生命周期资源。

## 延伸练习

- 增加一个 `withFormat(string $format): self` 方法，返回修改格式后的新对象。
- 把 `readonly` 去掉，再观察调用方是否能随意修改配置。
- 新增一个可变对象属性，思考 readonly 是否还能保证深层不变。
