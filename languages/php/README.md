# PHP

## 语言定位

PHP 的第一版学习基线是 **8.5.x**，工具链入口是 **PHP 8.5**。它主要用于：Web 应用、CMS、电商、业务后台。

PHP 的定位是为 Web 请求而生的服务器端语言：从模板嵌入 HTML 起步，发展到今天的类型增强、Composer 生态、成熟框架和长期运行服务。它的设计哲学很务实，强调“接住 HTTP 请求、读写数据、生成响应”这条主线。现代 PHP 不再只是零散脚本，而是可以用命名空间、类、属性、枚举、类型声明、依赖注入和测试构建大型业务系统。学习时要同时理解传统请求生命周期和现代框架工程实践。

## 适合场景

- 内容站、CMS、电商、后台系统和表单密集型 Web 应用：部署成熟，托管广泛，生态贴近业务。
- 团队需要稳定的 MVC/ORM/模板/队列/任务调度一体化体验时，Laravel、Symfony 等框架生产力很高。
- 适合围绕数据库、缓存、文件上传、邮件、支付和第三方 API 组合业务流程。
- 不太适合浏览器端交互、移动端原生核心、硬实时系统或需要长时间 CPU 密集计算的单进程任务。
- 不太适合把脚本随意堆在 Web 根目录中长期维护；现代 PHP 项目应依赖 Composer、框架入口和清晰分层。

## 核心语法

重点学习变量/常量、函数、模块、数据结构、泛型或类型标注、控制流，以及该语言最常见的代码组织方式。案例会尽量保持短小，让语法特征直接暴露出来。

PHP 语法围绕变量、数组、函数、类、命名空间、接口、Trait、属性、枚举和异常展开。数组既可当列表也可当映射，是强大也容易混乱的核心结构；现代代码中应区分顺序列表、关联数组和对象模型。惯用组织方式是 Composer 自动加载、`src/` 放业务代码、`tests/` 放测试、入口文件只负责交给框架或应用内核。函数式工具如 `array_map`、`array_filter` 可用，但业务逻辑通常更依赖清晰的对象、DTO、服务类和仓储边界。

## 类型/内存/并发模型

- 类型模型：动态类型增强、strict_types、union/intersection types。
- 并发模型：请求级并发、Fibers、队列。
- 内存与资源：结合语言自己的生命周期管理方式学习，不把所有语言都套成同一种范式。

PHP 是动态语言，但现代版本已经有标量类型、返回类型、属性类型、可空类型、联合类型、交叉类型、`mixed`、`never` 和枚举。`declare(strict_types=1)` 能减少隐式标量转换带来的意外，但它按文件生效，需要团队一致使用。PHP 没有内建泛型，复杂集合类型通常依赖 PHPDoc 和静态分析工具表达。

传统 PHP-FPM 模型是每个请求独立处理，内存和全局状态通常在请求结束后释放，这让部署和故障隔离简单。资源如文件句柄、数据库连接、curl 句柄仍要及时关闭或交给框架容器管理。并发主要来自 Web 服务器或进程池同时处理多个请求；异步任务常交给队列、定时任务或外部 worker。Fibers 为协作式调度提供基础，Swoole、ReactPHP、AMP 等生态可支持长连接和异步 I/O，但一旦进入常驻进程，就必须格外注意静态状态、内存泄漏和连接生命周期。

## 标准库与包管理

包管理入口：Composer。第一版案例优先使用标准库，只有框架章节才引入生态依赖。

PHP 标准库覆盖字符串、数组、日期、文件、流、JSON、哈希、过滤器、PDO、SPL 迭代器和异常体系。学习时要熟悉数组函数、`DateTimeImmutable`、PDO 预处理、过滤输入和文件上传处理。Composer 是现代 PHP 的项目骨架：`composer.json` 描述依赖、自动加载、脚本和平台约束，`composer.lock` 保证可重复安装。Packagist 提供主流包来源，但引入依赖前要确认维护状态、版本约束和安全公告。

## 错误处理

Throwable、Exception、Error、try/finally。学习时关注错误如何被表达、传播、恢复，以及如何避免把异常路径藏在业务逻辑里。

现代 PHP 中可捕获的顶层接口是 `Throwable`，业务失败通常抛 `Exception` 子类，类型错误、解析错误等多属于 `Error` 体系。要用 `try/catch/finally` 明确恢复点和资源清理，避免依赖 `die`、`exit` 或直接输出错误给用户。Web 应用中应把异常统一交给框架错误处理层，记录日志、返回合适 HTTP 状态和用户可理解的消息。数据库、文件、外部 API 错误要带上下文，但不要泄露密钥、SQL 参数或隐私数据。

## 工程化

第一阶段关注代码格式、测试入口、依赖声明和可重复运行。大型工程主题，如性能分析、发布、观测和安全，会在框架章节逐步展开。

现代 PHP 工程以 Composer、PSR 规范、自动加载和静态分析为中心。常见工具包括 PHPUnit/Pest、PHPStan/Psalm、PHP-CS-Fixer、Rector、Composer scripts 和框架自带 CLI。项目要明确运行方式：PHP-FPM、CLI worker、队列消费者、计划任务或常驻服务。工程化还包括环境变量、配置缓存、数据库迁移、日志、错误追踪、依赖安全扫描和部署回滚。对于团队项目，统一 `strict_types`、代码风格和静态分析级别，比追逐语法新特性更重要。

## 常见坑

- 只学习语法而忽略包管理和项目结构。
- 把其他语言的范式硬搬过来，错过本语言的惯用表达。
- 示例能跑但没有预期输出，导致无法判断自己是否真正理解。
- 松散比较 `==`、隐式类型转换和空值判断容易制造安全与业务漏洞。
- 把用户输入直接拼进 SQL、HTML 或 shell 命令，忽略预处理、转义和验证。
- 过度使用全局变量、静态状态和包含文件，导致测试困难和请求间状态污染。
- 不了解 PHP-FPM 请求生命周期，把常驻进程和普通请求代码混用。
- 忽略 Composer 锁文件和平台版本，部署后才发现扩展或 PHP 版本不匹配。
