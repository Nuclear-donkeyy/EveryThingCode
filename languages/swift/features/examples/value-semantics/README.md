# Value Semantics

## 目标

这个例子展示 Swift 为什么默认鼓励用 `struct`、`enum`、`let` 和受控的 `var` 建模业务数据。`Cart` 是值类型，复制后修改副本不会影响原始购物车；`ReferenceCounter` 是类，两个变量会指向同一个实例，用来对比引用身份带来的共享修改。

重点不是说类不好，而是看清取舍：当你要表达一份业务数据快照时，值语义更容易局部推理；当你确实需要共享身份或生命周期时，再使用类。

## 特性说明

Swift 的结构体默认是值语义。把 `original` 赋值给 `draft` 时，代码读者可以把它理解成复制了一份购物车状态。之后 `draft.add(...)` 是对副本的修改，不会悄悄影响 `original`。这对表单草稿、购物车、页面状态、网络响应模型特别重要，因为这些对象经常在多个函数之间传递。如果每个接收方都可能改同一份共享对象，调试时就要追踪所有引用路径；值语义把问题缩小到当前变量。

例子中的 `Cart.items` 是 Swift 标准库数组。数组也表现为值语义，但实现上使用写时复制。也就是说，赋值时不一定立即深拷贝底层存储，只有当某一份副本要修改时才需要分离。这让 Swift 可以同时追求清晰语义和实际性能。

如果不用这个特性，代码通常会退化成所有模型都写成可变类。短期看少写 `mutating`，长期会让“谁拥有数据”“谁能修改数据”“修改是否影响其他调用方”变得模糊。Swift 用值语义把默认方向调成局部、可预测、适合组合。

## 设计取舍

值语义的收益是状态变化更容易追踪，函数输入输出更像快照，测试也更简单。代价是你需要显式写出修改点，例如结构体方法要修改自身时必须标记 `mutating`；对很大的数据结构也要理解写时复制，不要在紧密循环里制造无意义的副本。

引用语义仍然有清晰用途。例子里的 `ReferenceCounter` 适合表达“同一个计数器实例”的身份：两个变量不是两份计数器，而是同一个对象的两个句柄。真实工程中的数据库连接、缓存、协调器、UI 控件、共享服务经常需要这种身份。Swift 的取舍不是禁用类，而是让值成为默认选择，让类成为有明确理由的选择。

## 运行

```bash
swift main.swift
```

## 观察点

- `var draft = original` 后，`draft.add(...)` 只改变副本，`original` 的商品数量保持不变。
- `Cart` 内部的 `items` 是数组，Swift 标准库用写时复制优化常见场景，所以值语义不等于每次赋值都立刻深拷贝。
- `ReferenceCounter` 的两个变量共享同一个实例，任何一边调用 `increment()` 都会改变同一份状态。
- 输出中的 `Original cart quantity: 3` 和 `Draft cart quantity: 6` 验证了购物车副本相互独立；`Shared class counter: 2` 验证了类实例共享身份。

## 延伸练习

- 把 `Cart` 改成 `final class Cart`，再运行一次，观察 `original` 和 `draft` 是否仍然独立。
- 把 `items` 改成 `private(set)` 以外的公开可变属性，思考调用方能否绕过 `add` 直接修改状态。
- 给 `Cart` 增加 `removing(_:)` 方法，让它返回一个新的 `Cart` 而不是修改自身，对比函数式更新和 `mutating` 更新的可读性。
- 增加一个嵌套的引用类型字段，观察“结构体本身按值复制，但内部引用仍可能共享”的边界。
