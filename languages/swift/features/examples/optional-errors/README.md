# Optional and Errors

## 目标

这个例子把 Swift 的 `Optional` 和错误处理放在同一条配置读取路径里。字典查询会得到 `String?`，因为键可能不存在；字符串转数字也会得到 `Int?`，因为内容可能不是合法数字。`loadPort` 用 `guard` 把这些缺失或无效情况转换成具体错误。

这样做的好处是调用方能区分“没有配置”“格式错误”和“超出范围”，而不是只得到一个空值或崩溃。

## 特性说明

Swift 把缺失值做成类型系统的一部分。`settings["port"]` 的结果不是 `String`，而是 `String?`，因为字典里可能没有这个键。`Int(rawPort)` 的结果也是 `Int?`，因为字符串可能无法解析成数字。只有通过 `guard let` 解包后，后续代码才能把它当成确定存在的 `String` 或 `Int` 使用。

这个例子进一步展示了 Optional 和错误处理的边界。Optional 适合表达“有或没有”，但它本身不携带详细原因。`loadPort` 在靠近失败发生的地方，把缺失、格式错误、范围错误转换成 `ConfigError`。调用方通过 `try` 看见这条路径可能失败，再用 `do/catch` 决定如何展示或恢复。

如果不用这些特性，代码通常会退化成默认值、哨兵值或强制解包。例如把缺失端口默认为 `0` 会隐藏配置错误；使用 `settings["port"]!` 会把可恢复问题变成崩溃；返回 `-1` 又要求所有调用方记住这个约定。Swift 的取舍是让不确定性先显式出现，再在合适的边界转换成有含义的错误。

## 设计取舍

Optional 的收益是轻量、直接，适合表示字段不存在、查找失败、转换失败等简单不确定性。它的代价是信息量有限，只有 `some` 或 `none`。当调用方需要知道失败原因，或者失败原因要跨层传递，就应该升级为 `throws`、`Result` 或领域状态枚举。

`throws` 的收益是顺序流程清楚：读取、解析、校验像普通代码一样从上到下写，失败时提前离开。代价是调用方必须处理 `try`，不能假装失败不存在。这个严格性在小脚本里显得啰嗦，但在配置、网络、文件和用户输入这类边界上，它能减少大量“失败被吞掉”的问题。

## 运行

```bash
swift main.swift
```

## 观察点

- `settings["port"]` 的类型是 `String?`，代码必须先解包才能继续使用。
- `Int(rawPort)` 也是 Optional，因为转换可能失败；这里把失败升级成 `ConfigError.invalidNumber`。
- `do/catch` 让调用点清楚看见 `try` 可能失败，并集中决定如何向用户展示错误。
- 输出中 `missing`、`text`、`tooLarge` 三种失败有不同消息，验证了错误枚举比单纯 `nil` 能保留更多上下文。

## 延伸练习

- 新增一个 `host` 配置项，要求不能为空字符串，并为缺失和空字符串设计不同错误。
- 把 `loadPort` 改成返回 `Int?`，观察调用方会丢失哪些错误信息。
- 尝试使用 `try? loadPort(...)`，看看它如何把所有错误折叠成 Optional，再思考这种写法适合哪些低风险场景。
- 给 `ConfigError` 增加 `recoverySuggestion`，练习把底层错误转换成面向用户的提示。
