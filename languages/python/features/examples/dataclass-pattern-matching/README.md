# dataclass-pattern-matching

## 目标

理解 `dataclass` 如何把“带名字的数据”变成清晰的领域对象，并观察结构化模式匹配如何按对象形状分派逻辑。

这个例子使用登录、购买和密码重置事件。较新的 Python 会执行真实的 `match/case` 分支；较旧的 Python 会走兼容实现，让 `python3 main.py` 仍然可以运行。

## 特性说明

这个例子对应两个经常一起出现的 Python 思想：用 `dataclass` 给数据边界命名，用 pattern matching 处理“不同形状的数据”。事件流、消息队列、审计记录和 API 输入都常常有固定字段。如果一直用字典传递，字段拼写错误、缺省值和展示格式会散落在调用处；如果手写普通类，又会为 `__init__`、`__repr__`、比较等样板代码付出额外成本。

`@dataclass(frozen=True)` 让 `Login`、`Purchase`、`PasswordReset` 成为轻量值对象：字段在类定义处集中声明，实例打印时可读，并且冻结后不容易在处理链中被意外修改。`match/case` 则把“这是哪类事件、字段满足什么条件、应该返回什么处理建议”放在同一组分支里。购买金额超过阈值、登录失败、管理员触发重置等业务差异，都可以通过对象类型、字段值和 guard 条件表达。

## 运行

```bash
python3 main.py
```

输出第一行会显示当前解释器使用的是 `match/case` 还是兼容的 `if/else` 路径。两条路径输出的业务结果相同，差异在于新语法把分派规则写得更接近“按事件形状阅读”。

## 设计取舍

`dataclass` 适合表达“主要由字段组成”的对象，但它不是完整领域模型的唯一选择。对象如果需要复杂不变量、懒加载、权限检查或数据库生命周期，普通类、工厂函数或专门校验库会更合适。本例使用冻结数据类，是为了强调事件一旦产生就不应在处理过程中被偷偷改写；真实项目里也可能保留可变对象，换取构造后补全字段的灵活性。

模式匹配能让分支紧凑，但也可能被滥用成巨大的中心调度器。如果每个事件都有大量行为，分派逻辑可能应该下沉到对象方法、注册表或插件机制里。兼容实现展示了不用 `match/case` 时的退化形态：代码仍然能工作，却需要多层 `isinstance` 和字段判断，读者要在多个缩进层里拼出“事件形状”。因此这个特性解决的不是“能不能判断类型”，而是“能不能把判断写成一张可读的业务规则表”。

## 观察点

- `@dataclass(frozen=True)` 让事件像值对象一样传递，不需要手写初始化方法。
- 模式匹配把“哪种事件、哪些字段值”放在同一个分支条件里。
- 兼容路径展示了没有 `match/case` 时同样逻辑会更分散，也更依赖手写判断。
- `Purchase(..., currency="USD") if amount >= 100` 说明模式可以先匹配字段，再用 guard 表达额外业务条件。
- 最后一条默认分支表示未知事件不会让程序崩溃，而是被明确归类为忽略。

## 延伸练习

- 新增一个 `Refund` 事件，包含 `user`、`amount`、`reason` 字段，并为高金额退款写一个单独分支。
- 去掉 `frozen=True` 后在循环中修改事件字段，观察这种可变性会如何影响调试和日志可信度。
- 把事件改成字典列表，重新实现 `describe_event()`，比较字段拼写错误在什么时候暴露。
- 在 Python 3.10+ 环境中把动态 `exec()` 改成直接的 `match/case` 函数，观察代码可读性与版本兼容之间的取舍。
