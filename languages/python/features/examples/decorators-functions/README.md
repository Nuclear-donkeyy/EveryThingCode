# decorators-functions

## 目标

理解 Python 函数是一等对象，并观察装饰器如何在不改业务函数主体的情况下加入审计、计时、缓存、重试等横切逻辑。

## 特性说明

这个例子对应 higher-order function、closure 和 decorator。`audit_step(label, audit_log)` 接收配置，返回真正的装饰器；装饰器接收一个函数，再返回包装函数 `wrapper`。`wrapper` 在调用原函数前后记录耗时和状态，业务函数 `parse_price()`、`apply_tax()` 仍只关心价格解析和税费计算。

装饰器解决的真实工程问题是复用横切逻辑。日志、权限、缓存、事务、指标采集和重试往往会出现在许多函数周围，如果每个函数都手写一遍，业务代码会被样板包围，还容易出现格式不一致。Python 允许函数像普通值一样传递，装饰器语法 `@...` 则把“用另一个函数包住这个函数”的意图放在定义处。

## 设计取舍

装饰器让公共逻辑集中，但也会增加间接性。读者看到 `parse_price("$12.50")` 时，实际执行的是包装后的函数；如果装饰器修改参数、吞掉异常或改变返回值，调试会变难。本例使用 `functools.wraps` 保留原函数名和元数据，让输出中的 `parse_price.__name__` 仍然可信，这是真实项目里写装饰器时很重要的小细节。

如果不用装饰器，代码通常会退化成在每个函数调用处写 `started = ...; try: ...; log.append(...)`。这种写法直接，但重复且容易遗漏。装饰器适合稳定、通用、围绕函数调用边界发生的逻辑；如果逻辑只属于某一个业务步骤，直接写在函数体里反而更清楚。

## 运行

```bash
python3 main.py
```

## 观察点

- `audit_step()` 返回 `decorate()`，`decorate()` 再返回 `wrapper()`，展示函数可以被创建、传递和返回。
- 输出中 `parse_price.__name__` 仍是原名，说明 `@wraps` 保留了函数元数据。
- 审计日志记录了两个步骤的成功状态和耗时，而两个业务函数没有手写审计代码。
- `audit_log` 被内部函数捕获，展示 closure 如何保存外层作用域里的状态。

## 延伸练习

- 让 `parse_price("bad")` 抛出 `ValueError`，观察审计日志如何记录失败，并思考异常是否应该继续传播。
- 新增一个 `@audit_step("discount", audit_log)` 函数，练习多个业务步骤共用同一个装饰器。
- 删除 `@wraps(function)`，观察 `__name__` 变成什么，理解元数据为什么重要。
- 把装饰器改造成统计调用次数的版本，比较“记录外部列表”和“闭包内部计数”的取舍。
