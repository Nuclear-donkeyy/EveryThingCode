# generators-iterators

## 目标

理解迭代器和生成器如何让数据处理变成惰性流水线，并观察 `yield` 如何一次产生一个结果，而不是先构建完整列表。

## 特性说明

这个例子对应 Python 的 iterator protocol 与 generator function。`parse_readings()` 接收文本行，解析出 `(name, value)`；`only_warm()` 过滤高于阈值的读数；`first_n()` 只取前几个结果。三个函数没有共享全局状态，也没有要求输入必须是列表，只要对象能被 `for` 迭代即可。

生成器解决的真实工程问题是“数据可能很大或来源很慢”。日志文件、CSV、网络流和数据库游标都不适合一次性读入内存。用 `yield` 写函数时，调用函数只会创建生成器对象；真正的解析发生在外层 `for` 循环向它索要下一个值时。这样每一层都只处理当前元素，流水线可以组合，也可以提前停止。

## 设计取舍

惰性迭代节省内存，并让处理可以短路。本例中 `first_n(..., count=2)` 找到两个符合条件的读数后就停止，后续行不会再被解析。代价是生成器只能向前消费一次，调试时也不能像列表一样随便查看长度或重复遍历。如果结果很小且需要多次访问，列表反而更清楚。

如果不用迭代器，代码通常会退化成“先解析全部行到列表，再过滤成第二个列表，再切片成第三个列表”。这种写法直观，但在大文件上会浪费内存，也会做一些最终用不到的工作。Python 用统一的迭代协议把列表、文件、字典视图、生成器和自定义对象连接起来，让函数可以面向数据流而不是具体容器。

## 运行

```bash
python3 main.py
```

## 观察点

- 程序先打印 `pipeline created`，说明创建流水线时还没有解析任何行。
- `parsed line ...` 与 `alert ...` 交错出现，说明数据是一条一条流过流水线。
- 由于只取两个高温读数，第四行不会被解析，提前停止节省了工作。
- 三个函数都接收 `Iterable`，返回 `Iterator`，展示了面向协议而不是面向列表的设计。

## 延伸练习

- 把 `count` 改成 `1` 或 `3`，观察哪些输入行会被真正解析。
- 把 `parse_readings()` 的输入换成从文件对象逐行读取，确认其他函数不需要变化。
- 在 `only_warm()` 前增加一个 `convert_f_to_c()` 生成器，练习把转换步骤插入流水线。
- 把每一步改成列表推导式，比较输出顺序、内存占用和提前停止能力。
