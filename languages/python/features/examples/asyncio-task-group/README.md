# asyncio-task-group

## 目标

理解 `asyncio` 如何把等待 I/O 的时间让出来，并观察 `TaskGroup` 如何把一组并发任务限制在同一个生命周期边界内。

这个例子并发读取三个模拟探针。Python 3.11 及以上会使用 `asyncio.TaskGroup`；旧版本会使用 `asyncio.gather()` 兼容运行。

## 特性说明

这个例子对应 Python 的协作式并发思想。很多程序慢，不是因为 CPU 一直在计算，而是因为大量时间花在等待网络、磁盘、定时器或外部服务响应。如果逐个等待三个探针，总耗时会接近所有等待时间之和；使用 `asyncio` 后，任务在 `await asyncio.sleep(...)` 处主动让出控制权，事件循环可以继续推进其他任务。

`TaskGroup` 是 Python 3.11 引入的结构化并发工具。结构化并发的核心不是“创建更多任务”，而是让任务有明确父作用域：在 `async with` 块中创建，在块结束前全部完成、失败或取消。这样任务不会悄悄漂在后台，也更容易推理失败传播。本例为了兼容 Python 3.9，保留了 `asyncio.gather()` 路径；两者都能并发等待，但 `TaskGroup` 更强调生命周期边界。

单个探针失败时，`safe_read_probe()` 把 `TimeoutError` 转换成普通结果对象。调用方因此可以展示整批状态，而不是因为一个探针超时就丢失其他成功结果。这是并发程序里常见的边界设计：任务内部处理可恢复错误，任务组负责组织生命周期。

## 运行

```bash
python3 main.py
```

输出会显示使用模式和总耗时。三个探针分别等待 0.30、0.10、0.20 秒；并发运行时总耗时应接近最慢的 0.30 秒，而不是 0.60 秒。

## 设计取舍

`asyncio` 适合大量 I/O 等待，尤其是网络连接、消息队列、定时任务和异步 Web 服务。它的代价是调用链需要显式 `async`/`await`，阻塞式函数如果混入事件循环，会让所有任务一起卡住。它也不是 CPU 并行方案；把 `sleep` 换成大规模纯 Python 计算后，单线程事件循环不会自动用满多核。

`TaskGroup` 比随手 `create_task()` 更容易收束任务，但它要求较新的解释器。本例用 `hasattr(asyncio, "TaskGroup")` 做运行时选择，是为了让学习材料在 Python 3.9 上仍可执行。如果项目已经明确要求 3.11+，真实代码可以直接使用 `TaskGroup`，并删除兼容分支，换取更直接的代码。

## 观察点

- `await asyncio.sleep(...)` 代表一次 I/O 等待，等待期间事件循环可以调度其他任务。
- `TaskGroup` 把创建任务和等待任务放在同一个 `async with` 块中。
- 单个探针失败被转换成结果对象，调用方仍能展示整批任务的状态。
- `elapsed` 接近最大单个延迟，说明等待被交错组织，而不是串行相加。
- 兼容路径中的 `gather()` 展示了旧版本也能表达并发，但结构边界没有 `TaskGroup` 明确。

## 延伸练习

- 把三个延迟都调大一倍，观察总耗时是否仍接近最慢任务。
- 去掉 `safe_read_probe()` 的 `try/except`，让一个任务真正抛错，比较 `TaskGroup` 和 `gather()` 的失败表现。
- 在 `read_probe()` 中加入一个阻塞的 `time.sleep(1)`，观察事件循环为何被卡住。
- 新增十个探针，并把输出按成功、失败分组，练习在并发结果返回后做同步汇总。
