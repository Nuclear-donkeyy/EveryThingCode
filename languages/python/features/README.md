# Python 特性与思想辅助教学

## 如何使用

这个模块把 Python 的语言思想和可以运行的短例子连在一起。建议先阅读“思想总览”，再按“核心特性地图”选择一个主题，进入对应例子目录运行 `python3 main.py`。运行时不要只看输出是否正确，也要观察代码如何组织数据、错误、资源和并发边界。

示例都只使用标准库。由于本仓库的 Python 学习基线面向较新的 Python 版本，而部分机器上的 `python3` 可能较旧，例子会在需要时提供兼容路径：新解释器展示真实特性，旧解释器仍然能运行并说明差异。

## 思想总览

Python 的核心取舍是把常见任务写得直接、可读，并把复杂度放在清晰边界里。它不是靠大量语法保护学习者，而是依赖命名、缩进、协议、异常和标准库约定，让代码像叙述问题本身一样展开。

这种设计也带来责任：动态类型让迭代很快，但公共边界需要更明确的数据模型；EAFP 让正常路径更干净，但异常必须捕获得足够具体；自动内存管理减少了手动释放对象的负担，但文件、锁、连接这类外部资源仍然要用 `with` 明确关闭；`asyncio` 可以让 I/O 并发写得紧凑，但任务生命周期不能散落在全局状态里。

## 核心特性地图

### 可读性与 duck typing

- 解决什么问题：真实项目里，很多函数只关心对象“能做什么”，不关心它属于哪个继承层级。例如日志对象只要有 `record()` 方法，数据行只要能按键读取，调用方就不必被具体类绑死。
- Python 为什么这样解决：Python 的动态绑定让代码天然面向行为协议。相比先设计庞大的接口树，Python 更鼓励用小函数、小对象和清晰命名表达意图，必要时再用类型标注或 `Protocol` 固化边界。
- 观察哪个例子：看 [context-manager-resource](examples/context-manager-resource/) 中 `process_orders()` 如何只依赖日志对象的行为，而不是要求某个复杂基类。

### dataclass 与模式匹配

- 解决什么问题：业务事件、配置、消息等数据需要既轻量又有名字。普通字典太松散，手写类又样板代码多；当事件种类变多时，靠一串嵌套 `if` 也会越来越难读。
- Python 为什么这样解决：`dataclass` 用很少代码声明“带字段的数据对象”，并自动补齐初始化、展示和比较等常见行为。结构化模式匹配 `match/case` 则把“按形状分派”的逻辑放在同一个表达式里，让读者看到每种数据形状对应的处理。
- 观察哪个例子：看 [dataclass-pattern-matching](examples/dataclass-pattern-matching/) 如何用不可变 `dataclass` 表达事件，再根据事件形状生成提示。

### 上下文管理器与资源边界

- 解决什么问题：文件、临时目录、锁、数据库连接和网络会话都不是普通内存对象，它们需要在明确时刻打开和关闭。只依赖对象析构，失败路径上很容易泄漏资源或留下半写入状态。
- Python 为什么这样解决：`with` 把“进入资源”和“离开资源”写成词法边界，`__enter__` 和 `__exit__` 让清理逻辑集中在资源对象里。调用方可以专注业务路径，资源对象负责无论成功还是失败都收尾。
- 观察哪个例子：看 [context-manager-resource](examples/context-manager-resource/) 中 `AuditLog` 如何在 `with` 结束时关闭文件，并把错误处理留在明确边界内。

### asyncio/TaskGroup

- 解决什么问题：网络请求、传感器读取、队列消费等 I/O 操作大量时间都在等待。如果逐个等待，程序简单但慢；如果随手创建任务，失败、取消和结果收集又容易失控。
- Python 为什么这样解决：`asyncio` 用协作式调度表达“等待时让出控制权”。`TaskGroup` 进一步提供结构化并发：一组任务在同一个块里创建、等待和收束，任务生命周期不飘在外面。
- 观察哪个例子：看 [asyncio-task-group](examples/asyncio-task-group/) 如何并发读取多个探针，并在旧版本解释器上对照 `gather()` 的兼容写法。

### 异常和 EAFP

- 解决什么问题：外部输入、文件系统、网络和用户操作都会失败。代码既要让正常路径清楚，也要让失败原因足够具体，避免用一堆提前检查把主流程淹没。
- Python 为什么这样解决：EAFP 是“先尝试，再处理明确异常”的风格。它适合动态对象和外部资源，因为“看起来能用”与“实际能用”之间常有竞态；真正执行并捕获具体异常，往往比提前猜测更可靠。
- 观察哪个例子：看 [context-manager-resource](examples/context-manager-resource/) 如何捕获数据缺字段和类型转换错误；再看 [asyncio-task-group](examples/asyncio-task-group/) 如何把单个任务失败转换成可展示结果。

## 深入理解与对比练习

### duck typing 的重点是协议，不是随意

Python 的灵活性很容易被误解成“什么对象都可以传”。真正可维护的 duck typing 依赖清晰协议：调用方只依赖 `write()`、`record()`、`__iter__()` 这类小行为，而不是偷偷假设对象内部结构。学习 `context-manager-resource` 时，可以新增一个只把日志写到内存列表的对象，只要它提供相同方法，业务函数就不需要改变。这个练习能帮助你区分“动态类型”与“无约束”。

### dataclass 是给边界命名

字典适合临时数据，但当数据穿过多个函数或模块时，字段名、默认值和不变量就需要被固定下来。`dataclass` 的价值是让数据形状显性化，又不迫使你写一堆样板类。运行 `dataclass-pattern-matching` 后，可以把事件改回字典实现，再比较模式匹配、自动展示和字段拼写错误的差异。你会发现 `dataclass` 不是为了“更像 Java”，而是为了让 Python 的动态表达更稳。

### with 是失败路径上的承诺

资源管理最容易在异常路径出错：正常执行时你记得 `close()`，一旦中间抛异常就可能跳过清理。`with` 把“无论如何都离开资源”变成语法结构，让清理逻辑不依赖调用者自觉。学习 `context-manager-resource` 时，故意在写入中途抛异常，观察 `__exit__` 仍然执行；再思考数据库事务、文件锁、临时目录为什么都适合这个模型。

### asyncio 解决等待组织，不解决 CPU 并行

`asyncio` 的优势在于大量 I/O 等待可以交错进行；如果任务是纯 CPU 计算，单线程事件循环并不会神奇变快。学习 `asyncio-task-group` 时，可以把每个探针的 sleep 时间调大，观察总耗时接近最慢任务；再把 sleep 换成大规模计算，你会发现事件循环被阻塞。这个对比能帮助你理解何时用 `asyncio`，何时考虑多进程、原生扩展或任务队列。

### EAFP 要捕获具体异常

EAFP 不是裸 `except`。好的 Python 代码会尝试执行最直接的操作，然后捕获明确、可恢复的异常，并保留足够上下文。比如解析订单时捕获 `KeyError` 或 `ValueError`，而不是吞掉所有 `Exception`。修改例子时，可以给输入加入缺字段、非法数字和空列表三种错误，分别写出不同处理分支，体会“正常路径干净”和“失败路径具体”可以同时成立。
