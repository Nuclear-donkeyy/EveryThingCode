# Interfaces and Composition

## 目标

这个例子展示 Go 如何用小接口和 struct 组合替代继承式扩展。`Service` 只依赖 `Notifier` 和 `AuditLogger` 两个行为，不关心具体类型来自哪里。`EmailNotifier` 没有写 `implements`，但只要方法集合匹配，就能作为接口使用。

例子也展示显式 `error`：发送失败时，调用点立刻看到 `err`，并用 `%w` 包装底层原因，保留可判断的错误链。

## 特性说明

接口组合对应 Go 的两个核心思想：接口由使用方定义，能力通过组合进入结构体。真实工程里，通知服务可能今天发邮件，明天换成短信、Webhook 或测试替身；如果业务服务直接依赖具体发送器，替换实现就会牵动核心流程。这里的 `Service` 只声明自己需要 `Notify(Message) error` 和 `Log(string)`，因此发送器和日志器可以独立演进。

如果不用这个特性，代码通常会退化成两种样子：一种是在 `Service` 里到处写 `if channel == "email"` 的分支，把业务流程和基础设施细节搅在一起；另一种是模仿继承体系，提前设计一个庞大的父类型，最后每个实现都被迫提供自己并不需要的方法。Go 的小接口让依赖边界更薄，也让测试替身更自然。

## 设计取舍

隐式接口让代码少了注册和声明成本，但也要求接口保持小而清晰。接口越大，越像“万能对象”，实现者越容易被迫依赖不相关的行为。这个例子把通知和审计拆成两个接口，是为了让调用方只拿到自己当前需要的能力。

组合不是继承的等价替代。它不会自动共享状态，也不会通过父类覆盖方法改变行为；这让代码少了一些“魔法”，但换来调用路径可读。错误处理也保持显式：`Service.Send` 发现发送失败后立即包装并返回，上层仍能用 `errors.Is` 判断 `ErrMissingRecipient`，说明补充业务上下文不必牺牲机器可判断性。

## 运行

```bash
go run main.go
```

## 观察点

- `Notifier` 是由使用方 `Service` 需要什么来定义的，而不是由实现方强迫所有通知类型继承同一个父类。
- `Service` 通过字段组合两个能力，测试或真实项目中可以替换成别的 notifier/logger。
- `errors.Is` 仍能识别被包装的 `ErrMissingRecipient`，说明补充上下文不等于丢掉根因。
- 输出先出现一次成功发送，再出现一次 `handled:` 错误；这能验证成功路径和失败路径都经过同一个服务边界。

## 延伸练习

- 新增一个 `SMSNotifier`，只实现 `Notify(Message) error`，再把它注入 `Service`，观察不需要修改 `Service.Send`。
- 写一个 `MemoryLogger`，把日志保存到 slice 中，模拟单元测试里断言日志顺序的做法。
- 给 `EmailNotifier` 增加一个新的哨兵错误，例如 `ErrEmptyBody`，并在 `main` 中用 `errors.Is` 区分不同失败原因。
