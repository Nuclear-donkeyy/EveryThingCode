# Defer Resource Cleanup

## 目标

这个例子展示 `defer` 如何把资源释放动作贴在资源获取动作附近。程序创建临时文件、写入报告、读取内容，并确保无论中途是否返回，文件关闭和临时文件删除都会执行。

真实工程里，文件句柄、网络连接、锁、事务和取消函数都不是垃圾回收能自动处理的业务资源。`defer` 解决的是错误路径容易漏清理的问题：资源一旦获取成功，就立即登记释放动作。

## 特性说明

`defer` 会把函数调用推迟到当前函数返回前执行，多个 defer 按后进先出顺序运行。例子中先登记删除临时文件，再登记关闭文件，所以返回时会先关闭再删除，符合资源依赖关系。命名返回值 `err` 让 defer 里的清理错误有机会补充到最终返回值中。

如果不用 `defer`，每个 `return err` 前都要手写 `Close`、`Remove` 或 `Unlock`。随着分支变多，最容易漏掉的就是错误路径，尤其是“写入失败后是否关闭”“提前返回后是否释放 timer”这类边界。`defer` 的价值不是少写一行，而是把资源生命周期变成局部、可检查的结构。

## 设计取舍

`defer` 有轻微运行时开销，但对绝大多数 IO 和服务代码来说，清晰的资源边界比这点成本重要。极端热路径可以在 benchmark 证明后再手动展开清理逻辑，不应提前牺牲可读性。这个例子也展示了清理错误的处理：如果主流程已经失败，通常先保留主错误；如果主流程成功但关闭失败，就把关闭失败作为最终错误返回。

需要注意的是，`defer` 绑定的是当前函数返回，而不是当前代码块结束。在长循环里对大量文件反复 `defer Close()`，可能导致文件直到函数结束才关闭。真实项目中可以把每次迭代拆成小函数，让 defer 的作用域刚好覆盖一次资源使用。

## 运行

```bash
go run main.go
```

## 观察点

- 输出中会先看到写入和读取内容，再看到 `close file`，最后看到 `remove temp file`，说明 defer 按后进先出执行。
- `defer` 紧跟在资源获取后面，读者不用在每个返回分支里搜索清理逻辑。
- `filepath.Base` 只打印临时文件名，避免不同机器上的临时目录路径影响观察重点。
- 即使你在写入后加一个提前返回，已登记的清理动作仍会执行。

## 延伸练习

- 在写入后直接 `return fmt.Errorf("simulate failure")`，观察清理输出是否仍然出现。
- 把关闭 defer 和删除 defer 的顺序调换，思考为什么删除前通常应该先关闭文件。
- 把文件处理逻辑放进循环，再拆成小函数，比较 defer 作用域对资源释放时机的影响。
