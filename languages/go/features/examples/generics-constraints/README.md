# Generics Constraints

## 目标

这个例子展示 Go 泛型如何用类型参数和约束复用一小段算法，同时保持静态类型检查。程序实现 `Sum` 和 `GroupBy`：前者只接受可相加的数值类型，后者保留输入元素和 key 的具体类型。

真实工程里，泛型常用于容器、集合操作、缓存包装、解析辅助函数和测试工具。它解决的是“同一算法因为类型不同而复制多份”的问题，而不是鼓励把所有业务模型都做成高度抽象。

## 特性说明

`type Number interface { ~int | ~int64 | ~float64 }` 是一个约束，表示类型参数 `T` 可以是这些底层类型之一。`~` 允许自定义类型使用同样的底层表示，例如 `type Score int` 也能参与求和。`GroupBy[T any, K comparable]` 则展示不同约束的含义：元素可以是任意类型，map 的 key 必须是可比较类型。

如果不用泛型，`SumInt`、`SumFloat64`、`SumScore` 这类函数会反复出现；如果改用 `interface{}` 和类型断言，调用方会丢掉编译期类型保证，错误更晚暴露。Go 的泛型把复用控制在函数和类型层面，不提供宏式元编程，故意让抽象保持可读。

## 设计取舍

Go 泛型的约束强调“这个算法真正需要什么操作”。`Sum` 需要 `+`，所以约束只列出支持相加的数值类型；`GroupBy` 需要 key 能放入 map，所以使用 `comparable`。这种写法比“接收任何值再运行时判断”更安全，也比为每种类型复制函数更容易维护。

代价是约束设计需要克制。约束过宽，函数内部可能无法使用想要的操作；约束过窄，调用方的自定义类型会被排除。Go 社区通常建议先写具体代码，重复稳定后再抽出泛型。这个例子里的函数都很小，目的就是展示泛型适合表达稳定算法，而不是替代普通接口和组合。

## 运行

```bash
go run main.go
```

## 观察点

- `Sum([]Score{...})` 能通过编译，说明 `~int` 接纳了底层类型为 `int` 的自定义类型。
- `GroupBy` 返回 `map[string][]Order`，调用方不需要类型断言就能继续访问 `Order` 字段。
- `K comparable` 不是装饰，它是 map key 的编译期要求；把 key 改成 slice 会直接编译失败。
- 输出同时包含分数总和和按地区分组的订单数，验证同一泛型函数能保留具体类型。

## 延伸练习

- 给 `Number` 增加 `~uint`，再用一个自定义 `type Count uint` 调用 `Sum`。
- 写一个 `Max[T ...]` 风格的函数时，先思考它真正需要哪些可排序类型，再用类型集合写出自己的约束。
- 把 `GroupBy` 的 key 函数改成返回 `[]string`，观察编译器如何提示 `comparable` 约束不满足。
