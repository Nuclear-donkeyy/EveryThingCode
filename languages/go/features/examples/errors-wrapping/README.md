# Errors Wrapping

## 目标

这个例子展示 Go 的错误包装：底层函数返回可判断的哨兵错误或结构化错误，调用链上的每一层用 `%w` 补充业务上下文，但不破坏上层用 `errors.Is` 和 `errors.As` 识别根因的能力。

真实工程里，日志需要人能读懂“哪一步失败”，程序也需要机器能判断“是否是用户不存在、权限不足、超时或临时网络错误”。错误包装就是把这两件事同时保留下来。

## 特性说明

Go 的 `error` 是普通返回值，`fmt.Errorf("...: %w", err)` 会把一个错误包进新的错误里。`errors.Is` 沿着错误链寻找指定哨兵值，`errors.As` 沿着错误链寻找指定错误类型。例子中的 `ErrUserNotFound` 适合表达稳定分类，`OperationError` 适合携带操作名和 key 这类调试上下文。

如果不用错误包装，代码通常会退化成字符串拼接：`return errors.New("deliver failed: user not found")`。这样日志看起来有上下文，但调用方只能靠字符串匹配判断原因，既脆弱又不利于本地化或重构。另一种退化是只返回底层错误，机器能判断根因，却丢掉“哪个用户、哪个操作”这样的排障信息。

## 设计取舍

哨兵错误适合少量稳定、跨包可判断的分类，不应该为每一条日志文案都定义一个哨兵。结构化错误适合携带上下文字段，但暴露出去后也会变成 API 承诺。这个例子把两者组合起来：`OperationError` 的 `Unwrap` 返回 `ErrUserNotFound`，外层再用 `%w` 增加“投递收据”的业务场景。

Go 不使用异常自动传播失败，因此每一层都要显式决定：处理、包装、转换还是返回。这带来一些 `if err != nil` 的重复，但失败路径不会藏起来。运行输出中同时出现完整错误文本和布尔判断，说明“给人看的上下文”和“给程序判断的根因”可以共存。

## 运行

```bash
go run main.go
```

## 观察点

- 成功路径会打印收据发送给已有用户，失败路径会打印一条带多层上下文的错误。
- `errors.Is(err, ErrUserNotFound)` 返回 `true`，说明 `%w` 没有丢失根因。
- `errors.As(err, &opErr)` 能取回 `OperationError`，因此上层仍可读取 `Operation` 和 `Key` 字段。
- 错误文本从外到内排列，适合日志排障；判断逻辑则不依赖这段文本。

## 延伸练习

- 增加一个 `ErrEmailDisabled`，让用户存在但关闭邮件时返回不同根因。
- 给 `OperationError` 增加 `Temporary bool` 字段，再用 `errors.As` 决定是否重试。
- 故意把 `%w` 改成 `%v`，重新运行并观察 `errors.Is` 为什么变成 `false`。
