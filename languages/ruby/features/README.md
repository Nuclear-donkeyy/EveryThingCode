# Ruby 特性与思想辅助教学

## 如何使用

本模块把 Ruby 的语言思想和可运行代码放在一起学习。建议先通读“思想总览”和“核心特性地图”，再进入例子目录运行 `ruby main.rb`。运行时不要只看输出是否正确，还要观察代码为什么能写成这样：对象如何接收消息，块如何把“要做什么”交给方法，协议如何替代显式接口，模块如何组合行为，Enumerable 如何表达数据流，`ensure` 如何守住资源边界，DSL 如何把领域规则组织成接近自然语言的 Ruby。

如果你已经学过 Java、C#、Go 或 TypeScript，可以特别留意 Ruby 的取舍。Ruby 不急着让编译器证明所有类型关系，而是把重点放在对象之间的消息协作、运行期组合能力和表达业务意图。它带来更高的表达弹性，也要求开发者用命名、测试和小接口控制边界。

## 思想总览

Ruby 的核心感受是“对象通过消息协作”。数字、字符串、数组、类本身几乎都能看作对象；调用方法就是给对象发送消息。集合处理经常通过 iterator 把遍历细节留给对象，把业务动作放进 block。对象能否参与某段逻辑，通常不取决于它继承了哪个接口，而取决于它是否响应调用方需要的方法，这就是 duck typing。

模块和 Enumerable 是 Ruby 日常代码中最重要的组合工具。模块让“可审核”“可序列化”“可验证”这类能力横向复用，不必为了共享少量方法建立深继承；Enumerable 则把集合、范围、文件行等“可逐项产生值”的对象放到统一操作模型中。两者都体现 Ruby 的偏好：先定义清楚的小协议，再让对象通过消息协作。

这些思想也解释了 Ruby 生态里大量 DSL 的来源。Rails 路由、Rake 任务、RSpec 断言看起来像小语言，本质上常由块、动态方法定义、开放类、模块和 `instance_eval` 等机制组合而成。Ruby 允许这样做，是为了让领域规则可以用接近业务语言的形式表达；代价是过度“魔法”会降低跳转、调试和重构的确定性。较新的 pattern matching 则补上了另一块表达力：面对结构化数据时，可以把“期望的形状”和“字段提取”写在同一处分支里。

异常处理体现了另一种 Ruby 风格：正常路径保持直接，失败路径用异常表达；资源释放则用 `ensure` 或块形式 API 明确兜底。学习时要理解 `ensure` 不是“处理错误”，而是“不管成功或失败都要收尾”的边界。

## 核心特性地图

### 一切皆对象

它解决的问题是让语言模型更一致：整数、字符串、数组甚至类都可以接收方法，学习者不必在“基本类型”和“对象类型”之间频繁切换。Ruby 用这种方式解决，是因为它把方法调用作为最基本的表达单元，统一对象模型能让 `3.times`、`"ruby".upcase`、`Array.new` 这类写法自然成立。请观察 `blocks-iterators` 例子，数字对象负责重复次数，数组对象负责遍历，业务逻辑被放在块里。

### block / iterator

它解决的问题是把“遍历怎么发生”和“每一步做什么”分开。Ruby 用 block 作为轻量闭包，让方法可以接收一段临时代码；`each`、`map`、`select`、`reduce` 等 iterator 则把集合遍历封装起来。这样写不是为了少几行循环，而是为了让数据流更接近人的阅读顺序。请观察 `blocks-iterators` 例子：订单筛选、折扣计算和汇总都由集合对象驱动，块只描述业务变化。

### Enumerable 管道

它解决的问题是把常见集合处理模式命名出来：过滤、转换、分组、聚合、排序不必都藏在一个手写循环里。Ruby 把这些方法放在 `Enumerable` 中，是因为很多对象只要能 `each` 产出元素，就能共享同一套数据流操作。学习者应该观察 `enumerable-pipelines` 例子：事件先被 `select` 和 `map` 清洗，再被 `group_by` 和 `transform_values` 聚合，最后排序输出。取舍是管道可能创建中间集合；数据量很大时要考虑 `lazy`、数据库聚合或流式处理。

### duck typing

它解决的问题是避免为了共享行为而建立过重的继承树或接口层。Ruby 用“能响应什么消息”来判断对象是否可用：只要对象有调用方需要的方法，就能放进同一流程。这样适合脚本、Web 业务和测试替身，因为这些场景常常需要快速组合小对象。代价是协议要靠清晰命名、错误信息和测试来维护。请观察 `duck-typing-protocols` 例子：控制台、内存缓冲和文件报告器没有共同父类声明，但都实现了 `write`。

### module / mixin

它解决的问题是横向复用行为，而不是把不相关对象塞进同一条继承链。Ruby 的 `module` 可以作为命名空间，也可以通过 `include`、`extend`、`prepend` 进入方法查找链。Ruby 选择这种方式，是因为动态消息派发和开放类模型让“组合一组能力”很自然。请观察 `modules-mixins` 例子：订单和部署对象都获得审核能力，但仍保留各自的领域身份。取舍是方法来源会增加，所以模块应小而具体，避免命名冲突。

### 元编程与 DSL

它解决的问题是把重复的样板代码压缩为领域声明。Ruby 的类和模块在运行期仍是对象，代码可以定义方法、读取块、改变接收者上下文，因此能构造小型 DSL。Ruby 选择开放这些能力，是为了让框架作者把常见模式做成可读的领域语言，例如任务定义、路由声明、测试规格。风险是调用链可能变得隐蔽，所以 DSL 应限制范围、保留清楚的错误提示。请观察 `dsl-metaprogramming` 例子：规则类用类方法收集字段定义，再生成实例方法完成校验。

### 异常和 ensure

它解决的问题是把失败路径和资源收尾表达清楚。Ruby 用 `begin` / `rescue` 捕获可恢复错误，用 `ensure` 保证清理逻辑一定执行。Ruby 也常提供块形式 API，比如 `File.open(path) { |file| ... }`，把 `ensure` 封装在库里。这样能让业务代码专注在正常路径，同时不忘记文件、连接、锁等外部资源边界。请观察 `ensure-resource-cleanup` 例子：手写 `ensure` 和块形式 API 都能保证文件关闭；也可对照 `duck-typing-protocols` 中的文件 writer。

### pattern matching

它解决的问题是让结构化数据的分支处理更集中。Ruby 的 `case ... in` 可以同时检查哈希或数组形状、匹配字面量、绑定局部变量。Ruby 用这种方式补强动态数据处理，是因为接口事件、JSON payload、解析结果常常先以哈希或数组进入程序，分支头部直接写形状比多层 `if event[:type]` 更清楚。请观察 `pattern-matching` 例子：付款、失败和退款事件由不同模式匹配并提取字段。取舍是它仍是运行期检查，协议变化要靠测试和兜底分支守住。

## 深入理解与对比练习

### Ruby 追求的是表达力和对象协作

Ruby 常被说“一切皆对象”，但学习重点不是把所有东西都写成复杂类层级，而是理解对象如何通过消息协作。方法调用、block、module、开放类和 DSL 都服务于表达力。阅读例子时，可以问：这段代码读起来像业务语言吗？对象之间的协作是否清楚？如果为了“优雅”隐藏了太多控制流，就需要把魔法收回来。

### block 是控制流的参数

block 让调用方把一段行为交给方法，方法决定何时、以什么上下文执行它。迭代器、事务、文件打开、测试 DSL 都建立在这个思想上。学习 `blocks-iterators` 时，把 `each` 改写成普通循环，再比较两者谁更突出业务意图。然后自己写一个接收 block 的方法，体会 Ruby 如何把“遍历方式”和“每项处理”分离。

### Enumerable 是可读数据流，不是炫技链条

学习 `enumerable-pipelines` 时，可以先把管道改写成单个 `each` 循环，再观察变量数量和职责边界的变化。Enumerable 方法名让过滤、转换、分组、聚合各有位置，但并不要求所有逻辑都写成一长串链式调用。好的 Ruby 代码经常在关键阶段命名中间变量，让调试输出和业务语言对齐。

### duck typing 要靠清晰协议支撑

Ruby 不要求类显式声明接口，但对象必须回应调用方需要的消息。学习 `duck-typing-protocols` 时，可以添加一个新对象，只要它实现同样方法就能参与流程。这个灵活性很适合插件和测试替身，但也要求你写清楚协议、错误信息和测试覆盖。否则“只要能 respond_to?” 会变成运行时才发现的脆弱约定。

### mixin 是能力组合，不是隐藏继承

学习 `modules-mixins` 时，重点观察 `ancestors` 输出：模块会进入方法查找链，因此它既强大也需要克制。把“可审核”做成 mixin 很自然，因为它是横切能力；但如果两个类共享大量领域状态，强行 mixin 可能只是把继承问题换了个名字。模块应小、命名具体，并且尽量依赖少量宿主方法或状态。

### 元编程和 DSL 应该服务重复结构

Ruby 的元编程可以生成方法、声明规则、构造接近自然语言的 DSL。它适合消除大量重复配置，但不适合把普通业务逻辑藏到难搜索的动态行为里。学习 `dsl-metaprogramming` 时，注意 DSL 如何把声明集中起来；再故意写一个过度动态的方法名，思考新人如何跳转、调试和重构。好的 DSL 应该让领域更清楚，而不是让实现者显得聪明。

### ensure 是资源边界的底线

异常在 Ruby 中很常见，`ensure` 保证无论是否抛错都执行清理逻辑。文件、锁、临时状态和外部连接都需要这种边界意识。修改 `ensure-resource-cleanup` 时，可以在 block 中抛异常，观察外层 ensure 是否仍然执行；再思考 Rails 中 around_action、事务块和文件块为什么都依赖类似模式。

### pattern matching 适合表达数据形状

学习 `pattern-matching` 时，可以把每个 `in` 分支改写成 `if` / `elsif`，比较哪种写法更容易看出输入契约。模式匹配不替代对象建模，也不替代测试；它适合在边界处整理结构化数据，再把已经识别的事件交给更明确的对象或方法处理。

## 学习检查

- 看到 `3.times`、`orders.map`、`String.new` 时，你能解释“接收消息的对象”分别是谁吗？
- 你能把一个手写 `for` 循环改成 `select`、`map`、`reduce` 的组合，并说明每个 block 承担什么职责吗？
- 如果两个类都能传给同一个方法，你能指出它们共同遵守的最小协议，而不是急着设计父类吗？
- 你能说明 module 进入方法查找链后的好处和风险，并判断某个共享行为是否适合做成 mixin 吗？
- 你能区分“适合 DSL 的重复声明”和“让维护者猜不出来源的元编程魔法”吗？
- 你能说明 `rescue` 和 `ensure` 的职责差异，并指出哪些资源需要无论成功失败都释放吗？
- 面对一段哈希事件数据时，你能写出 pattern matching 分支，并为未知形状保留兜底路径吗？
