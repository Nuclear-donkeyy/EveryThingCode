# blocks-iterators

## 目标

通过一个订单汇总小例子观察 Ruby 的对象模型、block 和 iterator。重点不是记住 `map` 或 `reduce` 的名字，而是理解集合对象负责“怎么遍历”，块负责“每个元素上做什么”。

这个例子对应 Ruby 的 blocks / iterators 思想：方法可以接收一段临时代码，集合对象可以把遍历细节封装在 `each`、`select`、`map`、`reduce` 这类方法里。真实工程中，报表汇总、导入清洗、权限过滤和订单结算都经常需要对一组对象做连续转换；iterator 让代码按“筛选、转换、汇总”的业务顺序阅读，而不是先陷入索引变量、临时数组和循环边界。

## 特性说明

Ruby 的 block 是轻量闭包，可以捕获外层变量，也可以由方法决定何时执行。`3.times { ... }` 中，接收 `times` 消息的是整数对象 `3`；`orders.select { ... }` 中，接收 `select` 消息的是数组对象。调用方只交出“每一项如何判断或转换”的 block，遍历顺序、结果收集和返回值约定则由 iterator 负责。

这个例子里，`select` 只保留已支付订单，`map` 把订单变成客户名和折后金额，`reduce` 汇总收入。三个 block 都很短，因为它们只表达当前一步的业务规则。如果不用这些特性，代码通常会退化为一个手写循环：先建立空数组，再在循环里判断状态、计算折扣、追加结果、更新总额。那样并不是不能工作，但“数据管道的阶段”会被可变变量和控制流细节盖住。

## 设计取舍

blocks / iterators 的优点是表达力强，尤其适合把集合处理写成连续的小步骤。它也鼓励小对象：`Order` 不需要知道报表规则，只要暴露 `status`、`total`、`customer` 等读取方法，集合管道就能组合它。

代价是过长的 block 会让管道变难读；如果一个 block 里出现多层条件、异常处理或外部副作用，就应该抽成命名方法或对象。另一个取舍是性能与中间数组：`select.map.reduce` 很清楚，但会创建中间结果；大量数据时可以考虑 `lazy`、数据库查询、流式处理或把步骤合并。学习阶段先追求意图清楚，再讨论是否需要优化。

## 运行

```bash
ruby main.rb
```

## 观察点

- `3.times` 展示数字也是对象，重复执行由数字对象接收 `times` 消息完成。
- `select`、`map`、`reduce` 都把业务动作放进 block，避免把遍历细节散落在业务代码里。
- `Order` 是普通对象，但只要提供读取方法，就能自然进入集合管道。
- 输出里只有 `paid` 订单进入 “Paid orders”，说明 `select` 的 block 决定了过滤条件。
- `Matz` 的金额从 `220` 变成 `198.0`，说明 `map` 的 block 在转换阶段应用了折扣规则。
- 最后的收入是两个已支付订单折后金额之和，验证 `reduce` 把前一步结果折叠成单个值。

## 延伸练习

- 给订单增加 `:refunded` 状态，修改 `select` 条件，观察收入是否排除退款订单。
- 把折扣规则抽成 `discounted_total(order)` 方法，比较命名方法和内联 block 哪个更清楚。
- 把 `orders.select.map` 改成 `orders.lazy.select.map`，再在末尾调用 `to_a`，观察惰性枚举器对阅读方式的影响。
- 故意把 `reduce(0)` 的初始值去掉，思考空数组时结果会有什么变化。
