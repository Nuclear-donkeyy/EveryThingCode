# enumerable-pipelines

## 目标

通过一组事件数据理解 Ruby 的 `Enumerable` 管道。例子展示 `select`、`map`、`group_by`、`transform_values`、`sum` 如何把“清洗、分组、聚合、排序”拆成可阅读的连续步骤。

这个例子对应 Ruby 标准库中 `Enumerable` 的思想：只要对象能逐项产出元素，就可以复用一整套集合操作。真实工程里的日志分析、CSV 导入、后台任务统计和接口响应整理，经常不是复杂算法，而是把一批记录按清楚的阶段转换成需要的视图。Enumerable 让阶段边界比循环变量更突出。

## 特性说明

`events.select.map` 先保留完成事件，再把原始事件转换成报表需要的哈希。`group_by` 根据用户分组，`transform_values` 对每组事件计算总秒数，`sort_by` 再按时长排序。每一步都返回普通对象，下一步继续接收消息，形成从原始数据到报表的管道。较新的 Ruby 也可以用 `filter_map` 合并过滤和转换；这里拆成两步，是为了兼容更旧的标准运行时，并让学习者看清两个阶段。

如果不用 Enumerable，代码通常会变成一个手写循环：在循环里判断事件类型、初始化哈希默认值、累加秒数、最后再排序。那样可控但容易把多个意图塞进同一个循环体，修改需求时也难判断某行属于清洗、分组还是聚合。Ruby 用 Enumerable 把常见集合模式命名出来，让读者通过方法名理解阶段。

## 设计取舍

Enumerable 管道的优点是语义密度高。`group_by(&:fetch)` 这种过度压缩不一定好，但 `group_by { |event| event[:user] }` 通常比手动维护分组哈希更接近业务语言。它还鼓励把中间结果命名，如例子中的 `completed` 和 `seconds_by_user`，便于调试。

代价是每一步可能创建中间集合；数据很大时，需要考虑 `lazy`、数据库聚合、流式读取或单次循环。另一个取舍是可读性：管道不应为了“链式”而链式。如果某一步规则复杂，抽成命名方法比把所有逻辑塞进 block 更稳。Enumerable 是表达数据流的工具，不是拒绝命名的理由。

## 运行

```bash
ruby main.rb
```

## 观察点

- 输出只统计 `:finished` 事件，说明 `select` 丢弃了未完成事件。
- `Ada` 的总时长来自两条完成事件相加，说明 `group_by` 后的每组仍可继续聚合。
- 排序结果按总秒数从高到低排列，说明管道最后一步改变的是展示顺序，而不是原始数据。
- `events` 仍是原数组，示例没有使用破坏性方法，便于在调试时回看输入。

## 延伸练习

- 增加一个 `:failed` 事件类型，统计失败次数并和完成时长一起输出。
- 如果你的 Ruby 支持 `filter_map`，把 `select.map` 改成一次 `filter_map`，比较两步更清楚还是一步更紧凑。
- 对空事件数组运行程序，观察 `sum` 和排序是否仍然稳定。
- 用 `lazy` 包住事件数组，思考大文件逐行处理时哪些步骤仍会迫使全部数据进入内存。
