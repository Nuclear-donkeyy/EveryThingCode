# ensure-resource-cleanup

## 目标

通过一个临时文件读取例子理解 Ruby 的 `ensure` 和块形式资源 API。重点是区分 `rescue` 与 `ensure`：前者处理可恢复错误，后者保证无论成功还是失败都执行清理。

这个例子对应 Ruby 的资源边界思想。垃圾回收会管理普通对象内存，但文件句柄、锁、网络连接、临时状态不应等 GC 随缘释放。真实工程中，导入文件、写日志、持有互斥锁、打开数据库连接都需要明确的收尾边界；Ruby 常用 `ensure` 或 `File.open(path) { |file| ... }` 这样的块形式 API 来表达。

## 特性说明

`read_with_manual_ensure` 手动打开文件，并在 `ensure` 中关闭它。即使 block 中抛出异常，`ensure` 仍会执行。`read_with_block_api` 则使用标准库已经封装好的块形式 `File.open`，Ruby 会在块结束后关闭文件。两者思想相同：资源由边界方法获取，也由边界方法释放。

如果不用这个特性，代码常会在成功路径末尾写 `file.close`，但一旦中途抛异常就跳过关闭动作。更糟的是，调用方可能看不出谁负责释放资源，导致重复关闭或泄漏。`ensure` 把“不管发生什么都要做”的逻辑放到语法层面，读者可以直接看到资源生命周期。

## 设计取舍

手写 `ensure` 的优点是明确，适合你正在封装一个新的资源 API。代价是每个调用点都要小心处理 nil、重复关闭和异常传播。块形式 API 更适合日常使用，因为释放逻辑集中在库里，调用方只写资源可用期间的业务代码。

`ensure` 不应该吞掉错误。它可以关闭文件、释放锁、恢复临时配置，但如果在里面随意 `rescue` 并忽略异常，原始失败会变得难排查。好的做法是让正常错误继续冒泡，只在你能真正恢复时使用 `rescue`。学习这个例子时，要把 `ensure` 看成边界的底线，而不是通用错误处理器。

## 运行

```bash
ruby main.rb
```

## 观察点

- 第一段输出会捕获一个故意抛出的错误，但仍显示文件已关闭，说明 `ensure` 没有被异常跳过。
- 第二段使用 `File.open` 的块形式，没有显式写 `close`，但块结束后文件同样关闭。
- 临时文件最后被删除，展示外部资源通常有多个生命周期边界：打开、使用、关闭、清理路径。
- 程序没有把 `rescue` 放进读取方法内部，说明读取方法负责收尾，调用方负责决定错误是否可恢复。

## 延伸练习

- 在 `ensure` 中打印更多状态，观察成功路径和失败路径都会经过它。
- 把 `file&.close` 去掉并在打开文件前抛异常，理解为什么收尾代码要考虑资源可能尚未创建。
- 写一个 `with_lock` 方法，用 `Mutex#lock` 和 `ensure` 封装 `unlock`。
- 把块形式 `File.open` 改回手动打开，比较哪种 API 更不容易被调用方误用。
