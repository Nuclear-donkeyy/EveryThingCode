# pattern-matching

## 目标

通过一组付款事件理解 Ruby 的 pattern matching。例子展示 `case ... in` 如何同时检查数据形状、提取字段和分派处理逻辑，适合处理结构化哈希、数组和简单值组合。为了让 `ruby main.rb` 在较旧 Ruby 上也能运行，示例会先检测版本：Ruby 2.7+ 使用真正的模式匹配，旧版本使用等价的哈希分支作为对照输出。

这个例子对应 Ruby 较新的模式匹配思想。真实工程里，接口事件、消息队列 payload、配置片段和解析结果经常是嵌套数据。传统 `if` / `elsif` 可以处理，但条件会分散在多个 `dig`、`key?` 和类型判断里。pattern matching 让“我期待的数据形状”直接写在分支头部。

## 特性说明

在支持 pattern matching 的 Ruby 中，`describe(event)` 使用 `case event`，再用多个 `in` 分支匹配哈希结构。`in { type: :payment, status: :captured, id:, amount: }` 同时要求事件类型和状态符合预期，并把 `id`、`amount` 绑定为局部变量。最后的 `else` 分支处理未知形状，避免静默忽略新事件。旧版本 fallback 则用普通哈希读取写出等价逻辑，方便你比较模式匹配减少了哪些重复判断。

如果不用 pattern matching，代码通常会写成多层条件：先判断 `event[:type]`，再判断 `event[:status]`，再取出字段并处理缺失值。那样对简单情况足够，但事件种类变多后，数据形状和处理逻辑容易分离。模式匹配把结构约束和变量提取放在一起，读者能快速看出每个分支消费什么输入。

## 设计取舍

pattern matching 的优点是分支表达清楚，尤其适合不可变或少变的数据消息。它能让未知输入尽早落入 `else`，也能减少手写 `nil` 检查。配合 Ruby 的哈希和数组字面量，读起来像是在声明输入契约。

代价是它不是静态类型系统。模式只在运行到该分支时检查，字段名拼错或上游结构变化仍需要测试覆盖。过度复杂的嵌套模式也会降低可读性；如果一个分支需要很多业务判断，先匹配外层形状，再交给命名方法处理会更稳。这个特性适合清楚表达数据形状，不适合把所有业务规则都塞进 `in` 一行。

## 运行

```bash
ruby main.rb
```

## 观察点

- 已捕获付款、失败付款和退款事件进入不同分支；在 Ruby 2.7+ 上，这说明模式同时检查了 `type` 与 `status`。
- 输出中直接使用 `id`、`amount`、`reason`；在模式匹配版本里，这些局部变量由 `in` 分支完成字段提取。
- 未知事件进入 `unhandled event`，说明 `else` 分支是处理协议演进的重要保护。
- 修改某个事件的键名后再运行，可以观察模式不匹配时控制流如何变化。

## 延伸练习

- 新增 `{ type: :payment, status: :authorized }` 分支，比较新增事件类型需要改动的位置。
- 把金额模式改成 `amount: 0..100`，观察范围模式如何表达更细约束。
- 添加一个嵌套客户哈希，如 `customer: { id:, tier: }`，练习嵌套结构提取。
- 去掉最后的 `else`，观察未知事件时 Ruby 的行为，再思考生产代码是否应该显式兜底。
