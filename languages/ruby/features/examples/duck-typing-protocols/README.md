# duck-typing-protocols

## 目标

通过多个报告输出对象理解 duck typing：调用方不关心对象属于哪个类，只要求它能响应 `write`。例子同时展示 `ensure` 如何保证文件资源在成功或失败后都被关闭。

这个例子对应 Ruby 的协议式思维：对象能否参与协作，取决于它是否响应调用方需要的消息，而不是是否显式继承同一个接口。真实工程里，日志输出、通知通道、支付网关、缓存后端、测试替身都常用这种方式替换实现。调用方保持稳定的小协议，实现方可以自由选择写到终端、内存、文件或远程服务。

## 特性说明

`ReportPrinter` 的需求非常小：它只需要一个对象能执行 `write(line)`。`ConsoleWriter`、`MemoryWriter`、`FileWriter` 没有共同父类声明，也没有接口关键字，但它们都遵守同一条消息协议，所以可以被同一个打印流程使用。这就是 duck typing 的核心：“如果它像鸭子一样响应需要的消息，调用方就把它当成可协作对象”。

这种方式解决了动态业务里的扩展问题。如果不用 duck typing，代码常会退化成 `case writer_type` 或一组 `if writer.is_a?(...)`，调用方被迫知道所有实现细节；或者为了一个 `write` 方法设计很重的继承树。Ruby 更鼓励把边界压缩成少量清晰消息，让对象在运行期组合。

例子里的文件写入还展示了资源边界。`FileWriter#close` 用 `ensure` 清掉内部引用；主流程也在 `begin ... ensure` 中关闭文件。这里的 `ensure` 不是“恢复错误”，而是保证无论打印成功、失败还是中途抛异常，都要执行收尾动作。

## 设计取舍

duck typing 的好处是扩展成本低。新增 `JsonWriter`、`HttpWriter` 或测试用的 `SpyWriter`，通常只要实现 `write` 就能接入现有流程。这让 Ruby 很适合插件、适配器和测试替身。

代价是协议不由编译器强制检查，错误会在运行时暴露。工程上要通过命名、文档、最小示例、测试和清楚的异常信息弥补。不要把 duck typing 误解成“什么对象都可以传”；它要求协议更小、更清楚，而不是没有协议。对于公共 API，可以用 `respond_to?` 做友好错误提示，但核心仍然是让调用方只依赖真正需要的消息。

## 运行

```bash
ruby main.rb
```

## 观察点

- `ReportPrinter` 只调用 `writer.write(line)`，这就是它需要的最小协议。
- `ConsoleWriter`、`MemoryWriter`、`FileWriter` 没有共同父类声明，但都能被同一个打印流程使用。
- `FileWriter#close` 使用 `ensure`，即使关闭时发生错误，也会清掉内部文件引用，避免对象继续持有失效资源。
- 输出先直接打印到控制台，再展示内存缓冲捕获的行，说明两个完全不同的对象遵守了同一个 `write` 协议。
- 临时文件被写入、读取、再删除，说明文件实现也能加入同一流程，但需要额外处理外部资源生命周期。

## 延伸练习

- 新增 `PrefixWriter`，让它包装另一个 writer，并在每一行前添加时间或级别前缀。
- 新增一个没有 `write` 方法的对象传给 `ReportPrinter`，观察 Ruby 抛出的错误，再思考如何给出更友好的协议检查。
- 让 `ReportPrinter#print` 在中途故意抛异常，确认外层 `ensure` 仍会关闭文件。
- 把 `MemoryWriter` 用在测试里，断言 `lines` 内容，体会 duck typing 如何降低测试替身成本。
