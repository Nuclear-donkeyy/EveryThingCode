# Ruby

## 语言定位

Ruby 的第一版学习基线是 **4.0.x**，工具链入口是 **Ruby stable**。Ruby 的核心定位不是“最快的脚本语言”，而是“让程序员表达意图时少受语法阻力”。它强调对象模型一致性、动态派发、块与迭代器、开放类和 DSL 写法。Rails 让 Ruby 成为 Web 开发的代表语言，但它同样适合自动化脚本、命令行工具和平台胶水代码。

学习 Ruby 时要接受它的设计哲学：很多事情在运行期发生，可读性和表达力比提前约束更受重视。Ruby 中几乎所有值都是对象，方法调用是基本操作；类、模块、混入、块、闭包和元编程一起构成表达空间。理解这些之后，Rails、RSpec、Rake 的“魔法”就会变成语言特性的惯用组合。

## 适合场景

Ruby 适合需求变化快、团队需要快速交付、业务规则比算法性能更复杂的场景。Web 后端、管理后台、内容系统、数据导入导出、接口编排、自动化运维和测试 DSL 都是它的舒适区。它的语法让领域概念容易落到代码里，块和枚举器适合表达数据转换流程。

不适合的场景也要提前识别：极致低延迟、高 CPU 密集计算、强静态约束的大型底层系统、移动端或嵌入式运行时通常不是 Ruby 的首选。C 扩展、JIT、队列和横向扩容能缓解部分性能问题，但实时计算或资源极限控制通常应选择贴近硬件的语言。

## 核心语法

Ruby 的变量无需声明类型，局部变量、实例变量、类变量、全局变量和常量通过命名形式区分。方法使用 `def` 定义，最后一个表达式默认作为返回值；括号常可省略，但工程代码里仍应保持一致。数组、哈希、范围、符号和字符串是日常数据结构，`each`、`map`、`select`、`reduce` 配合块，是处理集合的惯用方式。

类使用 `class` 定义，模块使用 `module` 定义。模块既可作为命名空间，也可通过 `include`、`extend`、`prepend` 混入行为。Ruby 没有传统接口语法，更依赖对象是否响应某个方法；因此命名和小对象设计很重要。惯用 Ruby 避免过深继承，偏好组合、模块混入和贴近业务语言的对象边界。块、`yield`、`Proc`、`lambda` 是理解 Ruby DSL 的关键。

## 类型/内存/并发模型

类型模型：Ruby 是动态类型语言，核心思想是 duck typing：对象的“可用性”取决于它能响应什么消息，而不是声明上属于什么类型。现代 Ruby 可以用 RBS 描述类型签名，也可用 Sorbet 做渐进式静态检查，但这些是工程辅助，不改变运行时的动态本质。学习时应理解协议式思维：稳定小接口比庞大继承层级更符合 Ruby 风格。

内存与资源：Ruby 使用垃圾回收管理对象生命周期，普通对象不需要手动释放。真正需要关注的是文件、网络连接、锁等外部资源，应使用块形式 API 或 `ensure` 保证释放。字符串、数组、哈希默认可变，传递集合时要清楚修改是否会影响调用方。

并发模型：MRI Ruby 有全局 VM 锁，线程适合 I/O 并发，但不适合在同一进程内并行跑大量 CPU 计算。Fiber 提供轻量协作式并发，常用于异步 I/O 调度；Ractor 通过隔离对象实现并行执行，但对可共享数据有更严格限制。实际工程中，Web 服务常结合多进程、多线程、后台任务队列和数据库锁来处理并发。

## 标准库与包管理

包管理入口：Bundler / RubyGems。RubyGems 负责发布和安装 gem，Bundler 负责按 `Gemfile` 与 `Gemfile.lock` 锁定项目依赖。学习阶段要养成使用 `bundle exec` 的习惯，避免系统 gem 与项目 gem 混用。标准库中常用 `json`、`csv`、`net/http`、`uri`、`fileutils`、`logger`、`optparse`、`minitest`，足以完成很多脚本和小工具。

生态上，Rails 是 Web 开发中心，Sinatra 适合轻量服务，RSpec 常用于测试，Rake 常用于任务编排，Rubocop 常用于风格检查。第一阶段案例会优先使用标准库，只有进入框架章节才引入生态依赖，这样能先看清语言本身，而不是被框架约定淹没。

## 错误处理

Ruby 使用异常表达失败，常见结构是 `begin`、`rescue`、`ensure`。`rescue` 不应过宽，尤其不要随手吞掉 `StandardError` 后只打印日志；更好的做法是捕获自己能恢复的错误，把无法处理的错误继续抛出。`ensure` 适合释放资源，块形式 API 则能把释放逻辑封装到库内部。

业务代码里可以定义显式领域错误，例如 `PaymentFailed`、`InvalidImportRow`，让调用方通过错误类型理解失败原因。对于可预期分支，也可以返回结果对象或状态值，不必把所有“不成功”都做成异常。重点是让错误路径可读、可测试、可观测。

## 工程化

Ruby 工程的最小结构通常包含 `Gemfile`、`Gemfile.lock`、`lib/`、`test/` 或 `spec/`，命令通过 Bundler 固定依赖环境。测试可以从标准库 `minitest` 开始，再根据团队习惯过渡到 RSpec。格式和静态检查常用 Rubocop，类型签名可用 RBS，命令行入口可放在 `bin/`。

大型 Ruby 项目要关注启动时间、依赖膨胀、数据库访问模式、后台任务幂等性和部署环境一致性。性能优化应先测量：很多瓶颈来自 SQL、网络 I/O、N+1 查询或对象分配，而不是语法本身。日志、指标、错误上报和安全更新也应作为工程默认项。

## 常见坑

- 只学习语法而忽略 `Gemfile.lock`、Bundler、测试入口和项目结构，导致示例远离真实工程。
- 把 Java/C# 式深继承或过度接口设计搬进 Ruby，反而错过 duck typing、小对象和模块组合的优势。
- 过度依赖元编程，短期代码很“聪明”，长期调试、跳转和重构困难。
- 不区分符号和字符串、可变和不可变、破坏性方法和非破坏性方法，例如 `map` 与 `map!`。
- 捕获过宽异常、吞掉错误、忘记在文件和连接场景中释放资源。
- 在 MRI 中误以为线程一定带来 CPU 并行，忽略进程、队列和 I/O 调度。
