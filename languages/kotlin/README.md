# Kotlin

## 语言定位

Kotlin 的第一版学习基线是 **2.3.x**，工具链入口是 **Kotlin 2.3**。它主要用于：Android、服务端、跨平台 UI。

Kotlin 的定位是“面向现代工程的务实静态语言”。它诞生于 JVM 生态，但目标不是把 Java 换个写法，而是在保持互操作的同时减少样板、强化空安全、提升领域表达能力，并通过协程让异步代码更接近顺序阅读。Kotlin 既能编译到 JVM，也支持 Multiplatform，在 Android、服务端、桌面和共享业务逻辑中都有位置。它的设计哲学偏实用：语法简洁但不追求极端纯函数式；类型系统更强，但仍允许与 Java 的历史世界共存。

## 适合场景

- 需要理解该生态的工程化默认选择，例如包管理、构建、测试和发布。
- 需要横向比较不同语言在类型、并发和错误处理上的设计取舍。
- 需要从小案例过渡到代表性框架，而不是只背语法。

Kotlin 特别适合 Android 新项目、希望减少 Java 样板的 JVM 服务、需要 DSL 的构建或配置场景，以及希望在多端共享模型和业务逻辑的团队。它也适合学习现代类型系统：空安全、密封层级、数据类、扩展函数和协程都能帮助你重新理解 API 设计。它不太适合对编译速度极度敏感的小型脚本集合，也不适合作为完全脱离 JVM 生态的系统语言入门。若团队大量依赖 Java 老框架，Kotlin 仍然可用，但需要认真处理平台类型、注解、反射和构建配置。

## 核心语法

重点学习变量/常量、函数、模块、数据结构、泛型或类型标注、控制流，以及该语言最常见的代码组织方式。案例会尽量保持短小，让语法特征直接暴露出来。

Kotlin 支持顶层函数和顶层属性，文件不必被类包住。`val` 表示只读引用，`var` 表示可变引用；这不等于对象本身不可变，所以集合要区分只读接口和可变实现。函数是一等公民，lambda、默认参数、命名参数、扩展函数和高阶函数是日常写法。数据建模常用 `data class`，单例和伴生对象用 `object` / `companion object`，有限状态或结果层级用 `sealed class` / `sealed interface`。

惯用法上，`when` 是强大的模式化分支；空值通过 `?`、`?:`、`?.` 和智能类型转换处理；`let`、`run`、`also`、`apply`、`with` 等作用域函数能减少临时变量，但过度嵌套会降低可读性。集合链式操作适合表达数据流，性能敏感时要理解中间集合、Sequence 和惰性求值。学习 Kotlin 语法时，不要只把 Java 代码机械翻译成更短的 Kotlin，而要思考 API 能否更明确地表达“是否为空、是否可变、状态是否穷尽”。

## 类型/内存/并发模型

- 类型模型：静态类型、空安全、协变/逆变。
- 并发模型：coroutines、Flow、structured concurrency。
- 内存与资源：结合语言自己的生命周期管理方式学习，不把所有语言都套成同一种范式。

Kotlin 是静态类型语言，类型推断能减少声明，但公共 API 仍建议显式写出返回类型。空安全是核心特性：`String` 与 `String?` 是不同类型，编译器会阻止很多空指针错误。泛型支持声明处和使用处变型，`out` 表示生产者协变，`in` 表示消费者逆变；inline + reified 能在部分场景保留类型信息。与 Java 互操作时会遇到平台类型，它们可能为空也可能非空，必须谨慎收窄。

在 JVM 上，Kotlin 的对象内存和 GC 主要服从 JVM 规则；在 Native 或 Multiplatform 场景中还要关注各目标平台差异。资源释放通常依赖 Java 的 `AutoCloseable` 和 Kotlin 的 `use`。并发方面，Kotlin 最重要的是协程：`suspend` 函数描述可挂起计算，`CoroutineScope` 管理生命周期，结构化并发要求子任务跟随父任务取消。`Flow` 适合异步数据流，但它不是普通集合；冷流、背压、调度器和取消传播都需要通过案例理解。

## 标准库与包管理

包管理入口：Gradle / Maven。第一版案例优先使用标准库，只有框架章节才引入生态依赖。

Kotlin 标准库提供集合扩展、字符串处理、范围、序列、Result、时间基础能力以及与 Java 标准库的桥接。服务端和 Android 项目通常使用 Gradle，Kotlin DSL 是常见选择；Maven 也可用，但复杂多平台项目多半会落到 Gradle。生态依赖要重点认识 `kotlinx.coroutines`、`kotlinx.serialization` 和测试工具。学习包管理时要分清 Kotlin 语言版本、Gradle 插件版本、JVM target、Android Gradle Plugin 版本和依赖库版本，它们不总是同步升级。

## 错误处理

异常、Result、sealed class 建模。学习时关注错误如何被表达、传播、恢复，以及如何避免把异常路径藏在业务逻辑里。

Kotlin 没有 Java 式受检异常，异常不会强迫调用方在签名里声明。因此，API 设计更需要主动选择错误表达方式：不可恢复的编程错误可以抛异常；可预期的业务失败可以用 `Result`、nullable 返回值或 sealed 层级表达。协程中的异常还涉及作用域取消，某个子协程失败可能取消整个父作用域；需要区分 `coroutineScope`、`supervisorScope` 和显式恢复策略。资源边界使用 `use`，不要把异常吞进 `runCatching` 后只返回空结果。

## 工程化

第一阶段关注代码格式、测试入口、依赖声明和可重复运行。大型工程主题，如性能分析、发布、观测和安全，会在框架章节逐步展开。

Kotlin 学习路径建议是：先用命令行或 Gradle 跑通 hello，再练习 data class、集合转换和空安全，然后学习协程与错误建模，最后进入 Android、Ktor、Spring Kotlin 或 Compose。工程上要熟悉 Gradle wrapper、source set、测试任务、JUnit/Kotest、MockK、ktlint、detekt 和 IDE 自动格式化。服务端项目还应关注启动时间、反射、序列化配置和 Java 框架互操作；Android 项目则要额外理解生命周期、主线程、协程 scope 与 UI 状态。

## 常见坑

- 只学习语法而忽略包管理和项目结构。
- 把其他语言的范式硬搬过来，错过本语言的惯用表达。
- 示例能跑但没有预期输出，导致无法判断自己是否真正理解。

Kotlin 常见坑包括：滥用 `!!` 把空安全退回运行时崩溃；把 `val` 误认为深度不可变；作用域函数连续嵌套导致 `it` 和 `this` 混乱；在协程里调用阻塞 I/O 却不切换调度器；忘记取消长期运行的 scope；忽略平台类型；为了简短写出难以调试的表达式链；在公共 API 中省略返回类型导致二进制兼容风险。判断一段 Kotlin 是否好，不只看短不短，还要看状态、错误和生命周期是否清楚。
