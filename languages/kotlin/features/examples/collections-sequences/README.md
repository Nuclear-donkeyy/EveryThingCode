# Collections Sequences

## 目标

理解 Kotlin 标准库集合操作和 `Sequence` 的差异：普通集合链更直接，会在每一步生成中间集合；`asSequence()` 让转换变成惰性流水线，通常只在需要结果时逐个推进。例子用订单报表展示两种写法的输出一致，但求值时机不同。

这个例子对应 Kotlin 的集合函数与 Sequence 思想。真实工程里，日志过滤、报表汇总、接口数据清洗经常需要 `filter`、`map`、`groupBy`、`sumOf` 这类组合；当数据量较大或只需要前几个结果时，理解 eager 与 lazy 的差别会影响性能和可读性。

## 特性说明

脚本先用普通 `List<Order>` 链式处理：筛出已支付订单，映射成收入条目，再按地区求和。这种写法清楚、适合大多数小到中等规模数据。随后脚本用 `orders.asSequence()` 构建惰性管道，并在 `filter` 和 `map` 中打印调试信息。只有调用 `take(2).toList()` 这个终端操作时，前面的步骤才真正执行。

`Sequence` 不是另一种集合，而是一条可迭代的计算描述。中间操作不会立即产生完整列表，终端操作才触发求值。它适合长链转换、潜在大数据、短路读取；但如果数据已经很小，或者需要多次遍历、随机访问、调试每一步，普通集合更简单。

## 设计取舍

集合操作的优势是把“怎么循环”降到背景里，把“筛选什么、转换什么、汇总什么”放到前台。没有这些函数时，代码通常会退化成可变 `MutableMap`、多层 `for`、手动累计金额和散落的临时变量，业务规则会混在迭代细节里。

Sequence 的代价是求值时机更隐蔽，调试时不能只看每个中间列表；小数据上还可能因为额外抽象没有收益。Kotlin 的惯用取舍是先写清楚的集合链，只有在数据量、短路需求或中间集合成本确实重要时再切到 `asSequence()`。

## 运行

```bash
kotlin main.kts
```

## 观察点

- 第一段输出按地区汇总已支付订单收入，说明 `filter`、`map`、`groupBy`、`sumOf` 可以组成可读数据流。
- Sequence 段会交错打印 `filter` 和 `map`，而不是先过滤完所有订单再映射所有订单。
- 因为有 `take(2)`，惰性管道只处理到拿到两个已支付摘要为止，这验证了短路求值。
- 两种写法都只用标准库；区别主要是求值策略，而不是业务结果。

## 延伸练习

- 把 `take(2)` 改成 `take(3)` 或去掉，观察 Sequence 调试输出变化。
- 在普通集合链的每一步后加 `also { println(it) }`，比较 eager 中间集合和 lazy 流水线的可观察差异。
- 新增一个 `refunded` 状态，并把已退款订单从收入中扣除，思考是继续链式组合还是先拆成命名函数更清楚。
