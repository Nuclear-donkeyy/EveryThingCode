# Null Safety

## 目标

理解 Kotlin 如何把“可能为空”放进类型系统，并用安全调用、Elvis 运算符和局部转换处理不完整输入。例子刻意包含缺失昵称、空白昵称和缺失邮箱，观察代码如何给出稳定输出。

这个例子对应 Kotlin 的空安全（null safety）思想：让 `String` 和 `String?` 成为两种不同类型，迫使调用者在编译期承认可空值的存在。真实工程里，用户输入、数据库字段、远程接口和 Java 互操作都可能产生缺失值；如果这些缺失值只靠注释约定，最容易在深层业务逻辑里变成空指针异常。

## 特性说明

`RawUser.nickname` 和 `RawUser.email` 都声明为可空类型，因此不能直接当成普通 `String` 调用所有操作。脚本里的 `displayName` 使用安全调用 `?.` 逐步处理昵称：只有昵称非空时才会 `trim`，只有清理后非空白时才会继续保留，否则通过 Elvis 运算符 `?:` 回退到 `匿名用户#id`。

`emailDomain` 返回 `String?`，因为“没有可用邮箱域名”本身就是合法结果。调用处再用 `?.let { ... } ?: ...` 把可空域名转换成可打印文字。这样一来，缺失值的处理被分成两个清楚层次：提取函数保留“不存在”的事实，展示层决定如何显示兜底文案。

## 设计取舍

空安全的代价是边界代码会更显式：你需要写出 `?.`、`?:`、`let`、早返回或错误结果，而不能假装值一定存在。收益是调用链中每一步都能看见风险，编译器会阻止把 `String?` 直接传给只接受 `String` 的函数。

如果不用这个特性，代码通常会退化成两种形态：一种是在每个地方手写 `if (value != null)`，但很容易漏掉嵌套字段；另一种是用 `!!` 或隐式约定把风险推迟到运行时，线上数据一旦不符合预期就崩溃。本例故意不使用 `!!`，因为教学重点是让缺失值成为可读分支，而不是把它变成晚爆炸的异常。

## 运行

```bash
kotlin main.kts
```

## 观察点

- `String` 和 `String?` 是不同类型，可空值不能当作非空值直接使用。
- `?.` 只在左侧非空时继续调用，`?:` 明确写出兜底策略。
- `takeIf` 和 `let` 可以把校验后的局部值继续向后传递。
- 脚本没有使用 `!!`，因为教学目标是把缺失值变成可读分支，而不是运行时崩溃。
- 运行输出里，`Lin` 会保留清理后的昵称和邮箱域名；缺失或空白昵称会回退成匿名用户；无效邮箱或空邮箱会显示“未提供”。这些现象验证了每个可空分支都被显式处理。

## 延伸练习

- 新增一个 `phone: String?` 字段，写一个 `maskedPhone` 函数：手机号为空或长度不足时返回 `null`，展示层再决定兜底文案。
- 尝试把 `emailDomain(user)` 的返回值直接赋给 `String` 变量，观察编译器报错，再思考这比运行时失败早在哪里。
- 把 `displayName` 改成在昵称为空时抛出 `IllegalArgumentException`，比较“缺失值是业务可接受状态”和“缺失值是输入错误”两种建模方式。
