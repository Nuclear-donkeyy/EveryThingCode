# threads-channels

## 目标

这个例子对应 Rust 的线程、所有权移动和 channel 消息传递思想。目标是理解并发不一定要共享可变状态：多个工作线程可以拥有自己的输入数据，把结果通过 channel 发送给汇总线程。示例启动两个传感器线程，每个线程发送若干 `Reading`，主线程从接收端汇总数量和平均值。

真实工程中，日志采集、后台任务、文件扫描、网络请求聚合都可以用类似思路。Rust 的并发模型强调先明确数据跨线程时是移动、共享只读，还是受同步保护的共享可变状态。这个例子选择消息传递，是因为它让所有权边界非常清楚。

## 特性说明

`mpsc::channel()` 创建多生产者、单消费者通道。`tx.clone()` 复制发送端句柄，让多个线程都能发送消息；`rx` 留在主线程中负责接收。`thread::spawn(move || { ... })` 中的 `move` 会把闭包用到的 `sensor`、`values` 和 `tx` 移进新线程，避免线程引用主线程即将失效的局部变量。

`Reading` 被发送时所有权从工作线程移动到 channel，再由主线程接收。主线程的 `for reading in rx` 会一直读取，直到所有发送端都被丢弃。示例里的 `drop(tx)` 很关键：主线程放弃自己手上的原始发送端，否则接收循环会以为还有发送者可能继续发送。

## 设计取舍

如果不用 channel，常见写法是多个线程同时修改同一个共享 `Vec` 或计数器。这需要 `Arc<Mutex<T>>` 等同步工具，适合确实需要共享状态的场景，但锁竞争、死锁和持锁范围都会成为设计问题。消息传递的取舍是让每条数据有清晰的所有权流向，减少共享可变状态。

Rust 并不禁止共享内存并发，而是要求类型表达安全边界。能移动到线程里的数据需要满足 `Send`，能被多线程共享引用的数据需要满足 `Sync`。标准库 channel 展示了另一种结构：让线程彼此不直接共享业务集合，只通过发送拥有所有权的消息协作。代价是需要设计消息类型和关闭协议。

## 运行

```bash
rustc main.rs -o /tmp/rust-feature-example && /tmp/rust-feature-example
```

## 观察点

- 输出中 temperature 和 humidity 的顺序可能交错，因为两个线程并发发送消息。
- 每条 `Reading` 只由一个线程构造，然后移动到主线程处理，没有共享可变集合。
- `drop(tx)` 让接收循环在两个工作线程结束后自然停止，验证 channel 关闭也是协议的一部分。
- `count` 最终为 5，说明主线程收到了两个生产者的所有消息。
- 如果删除 `move`，编译器会提示线程闭包可能借用不够久的数据，这体现了所有权规则延伸到线程边界。

## 延伸练习

- 给 `Reading` 增加时间戳字段，使用 `std::time::Instant` 或 `SystemTime` 观察消息产生时间。
- 把汇总逻辑改成按传感器分别统计平均值，可以使用 `std::collections::HashMap`。
- 故意不调用 `drop(tx)`，观察程序为什么不会结束，再解释发送端生命周期和接收循环的关系。
- 改用 `Arc<Mutex<Vec<Reading>>>` 实现同样功能，比较共享内存和消息传递的复杂度。
