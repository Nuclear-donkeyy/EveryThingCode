# lifetimes-references

## 目标

这个例子对应 Rust 的生命周期（lifetime）和引用设计。目标是理解：引用不是拥有数据的值，它只是指向某个已经存在的数据；生命周期标注不是让数据活得更久，而是描述多个引用之间的有效关系。示例中的 `Document<'a>` 持有 `title` 和 `body` 的字符串切片，真正拥有字符串的是 `main` 里的 `String`。

真实工程里，引用常用于解析器、配置读取、日志视图、网络协议字段等场景。程序希望避免复制大段文本，同时又不能返回指向临时变量的悬垂引用。生命周期让 API 明确说明：返回的引用来自哪个输入，结构体里的引用至少需要活到结构体使用结束。

## 特性说明

`struct Document<'a>` 表示 `Document` 中的 `&str` 字段都不能比被引用的数据活得更久。`title: &title` 和 `body: &body` 没有复制字符串内容，只是借用了 `String` 的内部文本。只要 `document` 还在使用，`title` 和 `body` 的所有者就必须仍然有效。

`fn longer<'a>(left: &'a str, right: &'a str) -> &'a str` 说明返回值要么来自 `left`，要么来自 `right`，因此返回引用的生命周期不能超过两个输入中较短的那一个。`first_sentence(text: &str) -> &str` 没有显式生命周期，是因为 Rust 的生命周期省略规则能推断返回值来自唯一输入。`describe` 同时从文档和 fallback 中选择一个引用，所以需要把关系写清楚。

## 设计取舍

如果不用引用，最直接的办法是到处返回 `String`，每次切片和摘要都分配新内存。这样 API 简单，但在处理大文本、高频请求或零拷贝解析时会浪费资源。如果不用生命周期检查，代码可能返回指向局部临时字符串的引用，运行后才暴露内存错误。

Rust 的取舍是：在需要表达借用关系的 API 边界多写一点类型信息，换取编译期排除悬垂引用。多数函数不需要显式生命周期，因为编译器可以推断；当结构体保存引用、函数从多个输入中返回引用时，标注就成为文档和约束。学习时不要把生命周期理解成“延长生命”，它只是描述真实存在的所有权关系。

## 运行

```bash
rustc main.rs -o /tmp/rust-feature-example && /tmp/rust-feature-example
```

## 观察点

- 输出中的标题和摘要都来自 `main` 中拥有的 `String`，`Document` 只是借用它们。
- `first_sentence` 返回 `body` 的一段视图，没有构造新的 `String`。
- `longer(document.title, fallback)` 返回两个输入之一，生命周期标注表达了这个选择的安全边界。
- 如果尝试在内部创建一个临时 `String` 并返回它的 `&str`，编译器会拒绝，因为临时值离开函数后就会被释放。
- `describe` 可以返回 fallback，也可以返回文档摘要；调用方只拿到一个安全的 `&str`，不需要知道分支细节。

## 延伸练习

- 把 `Document` 改成拥有 `String` 字段，比较构造成本、使用便利性和是否还需要生命周期参数。
- 在 `first_sentence` 中改用 `split_once('.')`，观察返回切片仍然来自输入。
- 给 `Document` 增加 `tags: Vec<&'a str>`，思考标签文本的所有者是谁。
- 尝试写一个返回局部 `String` 切片的函数，阅读编译器错误并解释它防止了什么问题。
