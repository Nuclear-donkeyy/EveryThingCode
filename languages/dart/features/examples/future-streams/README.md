# future-streams

## 目标

这个例子区分 Dart 中两种常见异步形状：`Future` 表示稍后得到的一次结果，`Stream` 表示按时间到达的多次事件。代码模拟加载多个用户摘要和生成报表进度，不依赖网络或外部包，却保留了真实应用中“等待 I/O”和“持续接收事件”的结构。

学习目标是判断什么时候该建模成一次结果，什么时候该建模成事件序列。一次 HTTP 响应、一次文件读取、一次权限检查通常适合 `Future<T>`；下载进度、WebSocket 消息、传感器读数、用户输入变化通常适合 `Stream<T>`。把两者混用会让调用方要么错过中间事件，要么被迫处理根本不会重复发生的流。

## 特性说明

`fetchUserSummary` 是 `Future<String>`：调用后立即返回一个代表未来结果的对象，真正的字符串稍后完成。`main` 使用 `Future.wait` 同时等待三个摘要，这在真实项目中常用于并行发起多个 I/O 请求，然后统一进入下一步。`await` 让代码读起来像同步流程，但等待期间事件循环仍然可以处理其他已就绪任务。

`buildReportProgress` 是 `Stream<String>`，通过 `async*` 和 `yield` 按步骤发出多个事件。`await for` 会逐个消费这些事件，并在流结束后继续执行后续代码。这个形状很适合进度提示，因为调用方不必等所有步骤完成才能看到状态变化。

## 设计取舍

如果不用 `Future`，异步结果常会退化成嵌套回调：成功回调、失败回调和后续逻辑散落在不同闭包里，错误传播和执行顺序都难读。`Future` 的代价是你必须明确哪些函数是异步的，并在调用处选择 `await`、组合或返回给上层。

如果不用 `Stream`，连续事件可能被塞进 `List<Future<T>>` 或一次性返回一个列表。这样会丢掉时间维度：调用方只能等所有进度完成后才看到结果。`Stream` 的代价是生命周期更复杂，真实项目里通常要考虑取消订阅、错误事件和背压。本例用 `await for` 保持最小形态，先突出“多次事件”的语言模型。

还要注意，`async/await` 不等于并行计算。这里的 `Future.delayed` 模拟的是等待 I/O；如果把大量 CPU 计算直接放进 async 函数，它仍然会占用当前 isolate。

## 运行

```bash
dart run main.dart
```

## 观察点

- `Future.wait` 收集多个一次性异步结果，适合“等全部完成再继续”的场景。
- `await for` 按顺序消费 `Stream` 事件，适合进度、消息、传感器读数等持续输入。
- `async/await` 让等待期间事件循环可以继续处理别的任务，但它不等于并行 CPU 计算。
- 真正耗 CPU 的工作应该考虑 isolate；本例的延迟只是模拟 I/O 等待。
- 运行输出会先等到三个用户摘要都完成，再逐条打印报表步骤，能直接看出一次结果和多次事件的差别。

## 延伸练习

- 把 `Future.wait` 改成逐个 `await fetchUserSummary`，观察输出顺序和总耗时预期有什么变化。
- 在 `buildReportProgress` 中增加一个 `throw Exception(...)`，再尝试用 `try/catch` 包住 `await for`。
- 给 `Stream` 增加更多步骤，或者让每个步骤返回包含百分比的 record。
- 思考如果这个例子变成 Flutter 页面，哪些输出适合 `FutureBuilder`，哪些输出适合 `StreamBuilder`。
