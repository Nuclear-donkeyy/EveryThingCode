# C / C++

## 语言定位

C / C++ 的第一版学习基线是 **C23 / C++23**，工具链入口是 **C23/C++23 compiler**。它主要用于：系统、游戏、音视频、数据库、性能核心。这里把 C 和 C++ 放在同一章，是因为很多工程会同时遇到两者：C 提供接近硬件和 ABI 的最小抽象，C++ 在此基础上提供类型系统、模板、RAII、标准库和零成本抽象。

学习时要区分两种心智模型。C 更像“显式管理内存和布局的可移植汇编级语言”，重点是指针、数组、结构体、生命周期约定和错误码。C++ 更像“以资源管理为中心的多范式系统语言”，重点是构造/析构、值语义、泛型、异常边界和标准库容器。

## 适合场景

C / C++ 适合对性能、内存布局、平台 API、延迟和二进制兼容性有硬要求的场景：操作系统、驱动、嵌入式、游戏引擎、浏览器、数据库、音视频、图形渲染、科学计算核心库，以及需要被多语言调用的基础库。C 常用于稳定 ABI 和硬件接口，C++ 常用于大型性能应用和复杂抽象。

它们不太适合安全要求高但团队缺少系统经验的快速业务项目，也不适合主要靠简单 CRUD 交付价值的服务端应用。若项目更需要内存安全默认值，可考虑 Rust；若更需要快速迭代和生态脚手架，可考虑 Go、Java、Python 或 JavaScript/TypeScript。

## 核心语法

重点学习变量/常量、函数、模块、数据结构、泛型或类型标注、控制流，以及 C / C++ 最常见的代码组织方式。C 的基础是头文件声明、源文件定义、`struct` 建模、指针传参、数组与字符串约定、`malloc/free` 或调用方提供缓冲区。C++ 在这些基础上增加 class、构造/析构、引用、函数重载、模板、命名空间、lambda、智能指针和标准库容器。

惯用 C 代码会明确所有权：谁分配、谁释放、缓冲区长度由谁保证、错误码如何返回。惯用 C++ 代码则优先使用 RAII 和标准库：`std::vector` 管理动态数组，`std::string` 管理字符串，`std::unique_ptr` 表达唯一所有权。模板很强，但要先学会值语义、移动语义、const 正确性、引用生命周期和接口边界。

## 类型/内存/并发模型

- 类型模型：静态类型、手动内存、模板元编程。C 类型系统相对直接，很多约束依赖约定和工具检查；C++ 类型系统更强，支持模板、概念、重载解析、类型推导和编译期计算。
- 并发模型：线程、原子、协程、执行器生态。现代 C++ 标准库提供 `std::thread`、`std::mutex`、`std::atomic` 和协程基础设施，但高层调度通常依赖框架或执行器生态。
- 内存与资源：C 需要手动管理分配、释放和错误路径清理；C++ 推荐用 RAII 把资源绑定到对象生命周期。资源不只是内存，还包括文件句柄、socket、锁和 GPU 对象。性能敏感代码要理解栈/堆、对齐、缓存局部性、拷贝/移动和虚函数成本。

## 标准库与包管理

包管理入口：CMake / Conan / vcpkg。C/C++ 没有像 Cargo 或 Go modules 那样完全统一的官方包管理体验，因此构建系统本身就是学习重点。CMake 常用于生成跨平台构建，Conan 和 vcpkg 负责第三方依赖获取与集成。第一版案例优先使用标准库，只有框架章节才引入生态依赖。

C 标准库提供内存、字符串、文件、数学、时间等基础能力，但接口偏底层。C++ 标准库提供容器、算法、迭代器、字符串、智能指针、IO、线程、chrono、filesystem、optional、variant、span、ranges 等能力。学习建议是：C 先掌握数组、指针和标准库边界；C++ 先优先使用标准库容器和算法，少写裸 `new/delete`。

## 错误处理

C 错误处理通常使用错误码、空指针、返回长度或 `errno`，调用方必须检查返回值，并在失败分支释放已获得资源。C++ 支持异常，也越来越常见 `std::optional`、`std::variant`、`std::expected` 风格的显式返回。学习时关注错误如何被表达、传播、恢复，以及如何避免把异常路径藏在业务逻辑里。

在 C 中，清理路径要写得非常清晰，常见做法是集中跳转到 cleanup 标签。C++ 中，RAII 能让异常路径自动释放资源，但项目需要统一异常策略：库边界是否允许抛异常，跨 C ABI 是否必须转成错误码，性能关键路径是否使用 expected。

## 工程化

第一阶段关注代码格式、测试入口、依赖声明和可重复运行。C/C++ 工程化要同时处理编译器版本、标准开关、告警级别、链接库、头文件搜索路径、平台宏和调试符号。大型工程主题，如性能分析、发布、观测和安全，会在框架章节逐步展开。

建议默认打开较严格的编译警告，并把 warning 当作早期反馈。常见工具包括 clang-format、clang-tidy、CMake presets、sanitizers、gdb/lldb、valgrind、perf 或平台 profiler。测试可以使用 Catch2、GoogleTest 或项目自带框架，但本章案例优先保持标准库和最小构建。真实项目还要关注 ABI 兼容、静态/动态链接和交叉编译。

## 常见坑

- 只学习语法而忽略包管理和项目结构，结果无法解释头文件、链接错误、库搜索路径和 CMake 目标之间的关系。
- 把其他语言的范式硬搬过来，例如在 C++ 中手写大量裸指针所有权，而不是使用 RAII 和标准库。
- 混淆数组和指针、对象生命周期和存储期，导致悬垂指针、越界访问、重复释放或内存泄漏。
- 忽略未定义行为，以为“在我机器上能跑”就代表正确。
- C++ 中滥用继承、宏和全局状态，或在不了解拷贝/移动成本时传递大对象。
- 示例能跑但没有预期输出，导致无法判断自己是否真正理解。
