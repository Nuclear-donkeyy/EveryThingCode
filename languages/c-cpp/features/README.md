# C / C++ 特性与思想辅助教学

## 如何使用

这一组材料把 C / C++ 的语言思想和可运行例子放在一起。建议先通读“思想总览”，再按“核心特性地图”挑一个主题运行对应例子。每个例子都只依赖标准库，可以直接用 C++23 编译器运行。运行时不要只看输出，还要回到源码里观察：对象什么时候创建、什么时候释放，数据是否发生拷贝或移动，模板参数如何影响同一段算法，range 管道是否惰性求值，错误是抛出还是作为返回值交给调用者判断，以及结构体字段顺序如何改变内存布局。

C / C++ 的学习重点不是背语法，而是理解边界：语言允许你贴近硬件，也要求你对生命周期、所有权、布局和错误传播负责。C 更强调显式约定，C++ 更强调用类型、构造/析构和标准库把约定固化下来。下面的例子偏 C++，但解释会不断指出它和 C 风格资源管理、错误码边界、二进制布局之间的关系。

## 思想总览

C / C++ 常被用在系统、游戏、数据库、音视频和性能核心代码中，因为它们允许程序员直接表达内存布局、对象生命周期和抽象成本。贴近硬件带来确定性：你可以关心对象是否在栈上、容器是否连续存储、一次函数调用是否会分配内存。但这种确定性不是免费获得的，错误的指针、越界访问、重复释放、悬垂引用和错误 ABI 假设都可能变成难排查的问题。

C++ 的一个核心方向，是把“必须手动遵守的规则”尽量变成“类型和对象生命周期自动执行的规则”。RAII 把资源释放放进析构函数；值语义让对象像数字一样可以独立拥有自己的状态；移动语义让昂贵资源可以转移所有权；模板和泛型让算法在编译期适配多种类型；ranges 把集合处理组合成可读的数据流；`expected` 把失败写进返回类型；结构体布局让程序员能理解二进制边界和缓存行为。它们共同服务一个目标：在不牺牲底层控制力的前提下，把复杂工程里的约定变得更可组合、更难忘记。

## 核心特性地图

### 贴近硬件与手动资源

它解决的问题是：程序需要明确控制内存、文件、锁、socket、GPU 句柄等资源的获取、使用和释放，并且在性能敏感路径中理解每个抽象的成本。C / C++ 用这种方式解决，是因为它们面向系统边界，必须能和操作系统 API、硬件寄存器、C ABI 以及固定二进制布局协作。学习者应该观察 `raii-resource-lifetime`：示例里故意模拟一个底层资源句柄，让你看到手动 `open/close` 风格如何被对象生命周期包起来。再观察 `memory-layout-structs`，它展示对象大小、对齐和字段偏移如何影响真实内存。

### RAII

RAII，Resource Acquisition Is Initialization，解决的问题是错误路径和提前返回时容易忘记释放资源。C++ 选择用构造函数获取资源、析构函数释放资源，是因为栈对象的生命周期由语言保证：离开作用域时析构一定发生，包括异常传播时。这样资源管理就不再散落在每个 `if` 分支里，而是集中在资源类型本身。学习者应该观察 `raii-resource-lifetime`：看 `ScopedHandle` 如何在正常返回和失败分支中都自动关闭句柄，并且关闭顺序与构造顺序相反。

### 值语义与移动语义

值语义解决的问题是让对象拥有独立状态，传递、返回和放进容器时行为清晰；移动语义解决的问题是大对象或独占资源在转交所有权时不必做昂贵深拷贝。C++ 用拷贝构造和移动构造表达这两种行为，是因为它既要保留“像 int 一样使用对象”的直觉，也要支持 `std::vector`、`std::string`、`std::unique_ptr` 这类拥有资源的类型。学习者应该观察 `value-move-semantics`：输出会标出拷贝和移动发生的时机，帮助你区分“复制内容”和“转移资源”。

### 模板/泛型

模板和泛型解决的问题是：同一种算法不应该为 `int`、`double`、`std::string` 或自定义类型重复写多份。C++ 选择编译期模板，是因为系统语言希望抽象在运行时尽量没有额外分派成本，同时让类型错误尽早暴露。代价是错误信息可能复杂，过度模板化也会增加编译时间。学习者应该观察 `templates-generic-algorithms`：同一个 `summarize` 算法通过迭代器和可调用对象处理不同容器，而调用处仍保留具体类型的性能特征。

### ranges 与标准算法

ranges 解决的问题是集合处理代码经常被下标、临时容器和循环边界淹没。C++ 选择在迭代器模型之上增加 range 和 view，是因为标准库已经围绕迭代器建立了大量算法，同时现代代码更希望接口直接接收“一个可遍历范围”。views 通常是惰性的，能把过滤、转换等步骤组合起来而不立即分配新容器；ranges 算法还支持投影，让排序和查找可以直接关注对象的某个字段。学习者应该观察 `ranges-algorithms`：同一组任务先被惰性管道过滤和转换，再用 `std::ranges::sort` 按优先级排序。

### 错误码/异常/expected 的取舍

错误码解决的问题是显式、稳定、容易跨 C ABI 和进程边界传递，但调用方可能忘记检查，清理路径也容易重复。异常解决的问题是把错误从深层调用传播到能处理的位置，并配合 RAII 自动清理，但项目必须统一异常边界，尤其是库接口、实时路径和 C 接口。`std::expected` 解决的问题是把“成功值或错误值”写进函数类型签名，让失败保持显式，同时避免异常控制流。C / C++ 没有单一答案，是因为不同边界的约束不同：底层 C API 常用错误码，内部 C++ 业务逻辑可能用异常，性能关键或 API 清晰度优先的代码可能用 `expected`。学习者应该观察 `error-handling-expected`：解析端口号时，成功值和错误原因都在返回类型中表达。

### 结构体布局、对齐与连续内存

结构体布局解决的问题是程序需要和二进制数据、硬件、缓存和跨语言边界打交道。C / C++ 允许使用 `sizeof`、`alignof`、`offsetof` 观察对象布局，是因为系统编程必须知道数据如何落在内存中。字段顺序、padding 和对齐会影响结构体数组的大小，也会影响缓存局部性。学习者应该观察 `memory-layout-structs`：两个字段相同但顺序不同的结构体可能有不同大小，`std::vector` 和 `std::span` 则展示连续存储和非拥有视图如何配合。

## 深入理解与对比练习

### C/C++ 的力量来自明确成本

C/C++ 让你靠近内存、布局、调用约定和编译产物，因此也要求你理解成本在哪里。一次拷贝、一次堆分配、一次虚函数调用、一次未定义行为都可能影响正确性或性能。学习这些例子时，不要只看输出；要问每个对象什么时候构造、什么时候移动、什么时候析构、谁拥有资源、哪段内存是连续的、错误是在类型里显式表达还是隐式传播。这个追问是 C++ 工程能力的核心。

### RAII 是资源生命周期的默认答案

RAII 的关键不是“析构函数会调用”，而是把资源释放绑定到对象生命周期。这样异常、早返回和多分支路径都不需要重复写清理代码。学习 `raii-resource-lifetime` 时，可以在中途抛异常或提前返回，观察析构仍然发生。再对比 C 风格的手动 `open`/`close`，你会更清楚为什么现代 C++ 鼓励用对象包住文件句柄、锁和内存。

### 值语义让局部推理更简单

值语义意味着对象像整数一样可以复制、传递、比较，调用方不必担心远处有人悄悄修改同一份状态。移动语义则让“转移昂贵资源”不必总是复制。学习 `value-move-semantics` 时，观察拷贝和移动的日志；再思考哪些类型应该可复制，哪些类型只应可移动。比如字符串可复制，唯一文件句柄通常应禁止复制但允许移动。

### 模板是编译期抽象

模板让算法可以作用于不同类型，同时在编译期生成具体代码。它适合表达容器、迭代器、数值算法和策略组合，但错误信息可能复杂，接口约束需要文档或 concept 帮助。学习 `templates-generic-algorithms` 时，可以把算法用于 `int`、`double` 或自定义类型，观察需要满足哪些操作。这个过程能帮助你从“模板很玄”转向“模板要求类型具备某些能力”。

### ranges 让意图更突出，但不会替你管理生命周期

ranges 管道让“过滤后转换再遍历”更接近业务表达，但 view 常常只是借用原始范围。学习 `ranges-algorithms` 时，可以在创建 view 后修改原容器，再遍历 view，观察惰性求值带来的结果变化。也要思考一个风险：如果 view 引用的容器已经销毁，代码就会出错。C++ 的抽象通常不隐藏生命周期问题，而是要求接口把生命周期表达清楚。

### 错误策略要按边界选择

C 常用错误码，C++ 可以用异常、`std::optional`、`std::variant`、`std::expected` 或错误码。没有一种策略适合所有层。底层高频代码可能偏错误码或 expected，构造失败和不可局部恢复的问题可能适合异常，缺失值适合 optional。学习 `error-handling-expected` 时，可以把一个例子改成返回 `std::expected`，再改成抛异常，比较调用方代码如何变化。

### 内存布局不是稳定序列化格式

学习 `memory-layout-structs` 时，可以把结构体想象成“编译器为当前平台安排的一块内存”，而不是天然可跨平台发送的字节格式。padding、大小端、ABI 和编译器选项都会影响二进制表示。真实协议和文件格式更常见的做法是逐字段编码；只有在共享内存、硬件映射或明确 ABI 的场景中，才会严格约束结构体布局。

## 学习检查

- 你能否指出一个资源类型的“获取点”和“释放点”，并解释提前返回时为什么不会泄漏。
- 你能否根据输出判断一次操作是拷贝还是移动，并说出移动后对象还能做什么、不能假设什么。
- 你能否把一个只处理 `std::vector<int>` 的函数改成接受任意范围或迭代器的模板函数。
- 你能否解释 view 管道什么时候真正执行，以及它借用的原容器需要活多久。
- 你能否为一个函数选择错误码、异常或 `expected` 风格，并说明选择依据是 ABI、性能、可恢复性还是调用方体验。
- 你能否根据 `sizeof`、`alignof` 和 `offsetof` 推断结构体中可能存在的 padding。
- 你能否解释为什么 C / C++ 的“接近硬件”既是能力，也是需要工程纪律约束的风险来源。
