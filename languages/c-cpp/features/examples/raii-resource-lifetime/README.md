# RAII 资源生命周期

## 目标

这个例子对应 C++ 的 RAII，Resource Acquisition Is Initialization。目标是理解“资源获取就是对象初始化，资源释放就是对象析构”这一思想，而不是把它只当成一个语法技巧。示例用 `ScopedHandle` 模拟文件句柄和 socket 句柄：构造函数打印 `open`，析构函数打印 `close`，中途失败时函数直接 `return false`。

这个特性解决的真实工程问题是资源释放路径太多。文件、锁、socket、数据库连接、GPU 句柄都需要成对获取和释放；如果释放代码散落在每个错误分支里，后续新增分支时很容易遗漏。运行例子时重点看失败路径：`send_report(false)` 在网络失败后提前返回，但两个已经打开的资源仍然按作用域退出顺序自动关闭。

## 特性说明

`ScopedHandle` 的构造函数负责把对象变成“持有一个有效资源”的状态，析构函数负责在对象离开作用域时调用 `close()`。C++ 语言保证局部对象会在作用域结束时析构，包括正常执行到函数末尾、提前 `return`、以及异常沿调用栈传播时。这个保证让资源管理从“调用者记得做清理”变成“资源类型自己定义清理规则”。

示例还删除了拷贝构造和拷贝赋值，因为一个底层句柄通常不能有两个独立所有者同时关闭。它允许移动构造和移动赋值，表示所有权可以从一个对象转移到另一个对象；被移动走的对象把 `open_` 设为 `false`，析构时不会再次关闭同一个资源。这个设计和 `std::unique_ptr`、`std::lock_guard`、文件流对象的思想一致。

## 设计取舍

如果不用 RAII，代码通常会退化成 C 风格的手动清理：每次 `open` 后都要在所有失败分支写 `close`，或者用 `goto cleanup` 集中释放。集中清理在 C 中是常见且有效的约定，但它依赖开发者维护每条路径，并且资源越多越容易出错。RAII 的优势是把释放逻辑封装进类型，让调用点看起来像普通局部变量。

RAII 的代价是类型设计必须认真处理所有权。能否拷贝、能否移动、析构函数是否可能失败、移动后对象保持什么有效状态，都要写清楚。析构函数通常不应该抛异常，因为它可能在栈展开期间运行；真正可能失败的关闭操作需要在显式 `flush` 或 `commit` 之类的函数中报告。这个例子为了突出生命周期，只用打印模拟系统调用。

## 运行

```bash
c++ -std=c++23 main.cpp -o /tmp/cpp-feature-example && /tmp/cpp-feature-example
```

## 观察点

- `ScopedHandle` 不能拷贝，只能移动，因为一个句柄只能有一个所有者。
- `return` 发生在函数中间时，局部对象仍然会按作用域规则析构。
- 资源释放代码集中在析构函数中，而不是散落在每个错误分支里。
- 成功路径和失败路径都会打印 `close`，而且关闭顺序与局部对象构造顺序相反。
- 如果把 `ScopedHandle socket` 放进更小的 `{}` 作用域，可以观察它比 `file` 更早析构。

## 延伸练习

- 在 `send_report` 中加入第三个资源，比如 `ScopedHandle lock{"report-lock"}`，再在不同位置提前返回，确认所有资源都能释放。
- 去掉 `ScopedHandle(const ScopedHandle&) = delete`，尝试复制一个句柄，思考为什么两次析构会造成重复关闭。
- 把 `send_report` 的失败分支改成 `throw std::runtime_error`，在 `main` 中捕获异常，观察 RAII 是否仍然完成清理。
- 为 `ScopedHandle` 增加一个显式 `release()` 函数，比较“转交裸句柄给外部 API”和“由对象自己关闭”两种边界的风险。
