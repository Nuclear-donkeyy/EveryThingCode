# ranges 与标准算法

## 目标

这个例子对应 C++20/23 的 ranges、views 和 `std::ranges` 算法。目标是理解现代 C++ 如何把“遍历、过滤、转换、排序、查找”写成围绕范围的组合，而不是在每个地方手写下标循环。示例用一个任务列表展示：先通过 view 得到未完成任务标题，再按优先级排序，最后找到下一个紧急任务。

这个特性解决的真实工程问题是集合处理逻辑容易被循环细节淹没。业务代码想表达的是“未完成任务的标题”“按优先级排序”“找到紧急项”，但传统循环经常混入索引、临时容器和边界判断。ranges 让代码更接近数据流，同时保留 C++ 对类型、迭代器和分配成本的控制。

## 特性说明

`tasks | std::views::filter(...) | std::views::transform(...)` 创建的是惰性 view 管道。它并不会立刻复制所有标题到新容器，而是在 `for` 循环遍历时逐个过滤和转换。`std::ranges::sort(tasks, std::greater<>{}, &Task::priority)` 展示 ranges 算法的投影参数：排序比较的是 `Task::priority`，而不是整个 `Task` 对象。

`std::ranges::find_if` 直接接受容器，不需要手写 `tasks.begin(), tasks.end()`，返回值仍然是迭代器，因此可以和容器边界比较。ranges 的核心思想不是消灭迭代器，而是把“一个可遍历范围”作为更自然的接口，同时继续兼容标准库算法的性能模型。

## 设计取舍

如果不用 ranges，代码通常会退化成多个 `for` 循环：先创建临时 `std::vector<std::string>`，再手写排序 lambda，再手写查找逻辑。这样做直观但容易重复，尤其当过滤条件和转换逻辑在多个地方出现时，业务意图会散在循环体里。ranges 的优势是表达力和组合性，常见集合操作可以像管道一样阅读。

ranges 的代价是类型变复杂，view 的生命周期也要谨慎。惰性 view 往往引用原容器，如果原容器已经销毁或被不合适地修改，view 就可能失效。对于很短的简单循环，手写循环可能更清楚；对于需要复用、组合或强调意图的集合处理，ranges 更有优势。真实项目中要在可读性、编译时间和调试体验之间平衡。

## 运行

```bash
c++ -std=c++23 main.cpp -o /tmp/cpp-feature-example && /tmp/cpp-feature-example
```

## 观察点

- `active_titles` 没有声明成 `std::vector`，它是一个 view 管道，遍历时才产生标题。
- 排序后的输出按 `priority` 从高到低排列，说明 `std::ranges::sort` 的投影参数生效。
- `find_if` 返回的迭代器指向排序后的第一个紧急未完成任务，因此输出会跟排序结果一致。
- 管道表达的是“过滤后转换”，比手写循环更容易看出数据处理顺序。

## 延伸练习

- 在打印 `active_titles` 前把某个任务的 `done` 改成 `true`，观察惰性 view 是否反映最新状态。
- 把 `transform` 改成返回 `std::pair<std::string, int>`，同时打印标题和优先级。
- 用 `std::ranges::count_if` 统计未完成任务数量，比较它和手写循环的可读性。
- 故意让 view 引用一个局部临时容器，思考为什么 ranges 代码尤其需要注意生命周期。
