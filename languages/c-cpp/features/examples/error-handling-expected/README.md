# expected 显式错误处理

## 目标

这个例子对应 C++23 的 `std::expected` 风格错误处理。目标是理解一种介于错误码和异常之间的写法：函数签名直接说明“要么返回成功值，要么返回错误值”。示例中的 `parse_port` 把字符串解析成端口号，成功时返回 `int`，失败时返回 `ParseError`，调用者必须在使用结果前判断当前分支。

这个特性解决的真实工程问题是错误传播的可见性。解析配置、校验输入、调用底层 API 时，失败经常是业务流程的一部分，而不一定是异常事件。把失败写进返回类型后，调用点可以清楚看到错误来自哪里，也可以选择立即处理、转换成日志、或继续向外返回。

## 特性说明

`std::expected<int, ParseError>` 表示成功时携带 `int`，失败时携带 `ParseError`。`parse_port` 在遇到空字符串、非数字字符或端口范围溢出时返回 `std::unexpected(...)`；调用者用 `if (auto port = parse_port(input))` 判断是否成功，成功分支用 `*port` 取值，失败分支用 `port.error()` 读取错误原因。

和普通错误码相比，`expected` 不会把成功值和错误值拆成多个输出参数，也不需要调用者记住“返回 -1 表示失败”这样的隐式约定。和异常相比，它不会跳过调用栈，控制流就在当前表达式附近展开，适合需要显式处理失败的库接口、解析器、网络协议和性能敏感路径。

## 设计取舍

如果不用 `expected`，代码可能退化成几种形式：返回 `bool` 再通过引用参数输出端口号；返回特殊值如 `-1`；抛异常；或者把错误写进全局状态。这些方式不是都错，但各有边界。引用输出参数让接口不够直观，特殊值容易和合法值冲突，异常适合跨层传播但不适合所有项目边界，全局状态会破坏可测试性。

`expected` 的代价是调用方要显式分支，连续调用多个可能失败的函数时会出现样板代码。C++23 标准库的 `expected` 也不像一些函数式语言那样内建完整的 `and_then` 管道风格；真实项目可能会封装辅助函数，或在更高层使用异常。选择错误策略时要看边界：跨 C ABI 通常用错误码，构造失败或不可局部恢复的问题可能用异常，输入校验和协议解析很适合 `expected`。

## 运行

```bash
c++ -std=c++23 main.cpp -o /tmp/cpp-feature-example && /tmp/cpp-feature-example
```

## 观察点

- 输出中 `"443"` 进入成功分支，其他输入进入不同错误分支，说明错误原因没有被压扁成一个通用失败值。
- `parse_port` 的函数签名已经暴露失败类型，调用者不需要阅读函数体才知道它可能失败。
- 成功值和错误值不能同时存在，避免了“返回值无效但仍被使用”的常见接口歧义。
- 如果忽略返回值，编译器和代码审查更容易发现，因为结果是一个明确的对象而不是隐藏异常。

## 延伸练习

- 把 `ParseError` 改成包含错误位置的结构体，例如 `struct ParseError { std::string message; std::size_t offset; };`。
- 新增一个函数 `connect_to_port(int)`，也返回 `std::expected<std::string, ParseError>`，比较连续错误处理会产生多少样板代码。
- 把 `parse_port` 改成抛异常，再比较 `main` 中调用方代码的可读性和错误处理位置。
- 把错误类型改成 `std::string`，思考枚举错误和文本错误在国际化、日志和自动化判断上的差异。
