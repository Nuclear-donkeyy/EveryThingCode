# 模板与泛型算法

## 目标

这个例子对应 C++ 的模板、concept 约束和泛型算法思想。目标是理解“算法只依赖需要的能力，而不是依赖某一个具体容器”。示例中的 `summarize` 只接收一对迭代器和一个投影函数，因此同一段代码既能处理 `std::vector<Reading>`，也能处理 `std::array<int, 4>`。

模板解决的真实工程问题是重复实现。没有泛型时，你可能会为 `vector<int>`、`vector<double>`、数组、自定义结构体各写一份求平均逻辑；这些版本容易在边界条件、错误修复和性能优化上逐渐分叉。模板让算法在编译期根据实参类型生成具体代码，调用点保留类型信息，通常不需要运行时虚函数分派。

## 特性说明

`summarize` 的模板参数是 `Iterator` 和 `Project`。它并不关心迭代器背后是什么容器，只要求能 `++it`、能比较 `it != last`、能解引用 `*it`，并且 `project(*it)` 可以转换成 `double`。这些要求通过 `requires` 表达，目的是把接口契约写在函数签名附近，让不满足约束的调用尽早在编译期失败。

投影函数是泛型算法常见的扩展点。对于 `Reading`，调用方传入 lambda 取出 `reading.value`；对于 `int`，投影函数直接返回分数本身。算法主体没有 `if` 判断类型，也没有继承层次。标准库的 `std::sort`、`std::accumulate`、`std::ranges` 算法都采用类似思想：让容器负责存储，让迭代器或 range 暴露遍历方式，让算法只表达计算本身。

## 设计取舍

如果不用模板，常见退化方式是复制粘贴多个重载，或者把数据统一塞进某个基类指针集合里再用虚函数处理。前者维护成本高，后者增加运行时分派、堆分配和对象布局约束。模板的优势是零成本抽象和强类型检查；代价是编译时间可能变长，错误信息有时较复杂，模板实现通常需要放在头文件中暴露给编译器。

concept 和 `requires` 能改善模板接口的可读性，但它们不是魔法。约束太弱会让错误落到函数体深处，约束太强又会拒绝本来可用的类型。这个例子只约束投影结果能转成 `double`，而没有完整约束迭代器类别，是为了保持代码短小。真实库代码会使用标准概念如 `std::input_iterator`、`std::ranges::range` 和 `std::invocable` 表达更完整的契约。

## 运行

```bash
c++ -std=c++23 main.cpp -o /tmp/cpp-feature-example && /tmp/cpp-feature-example
```

## 观察点

- `summarize` 的算法主体只写一次，调用点决定元素类型和投影方式。
- 模板在编译期为具体类型生成代码，通常不需要运行时虚函数分派。
- 约束写在 `requires` 中，错误会尽量停在“不满足接口”的位置。
- `Reading` 和 `int` 没有共同基类，算法仍然可以复用，因为它只依赖投影后的数值。
- 空范围返回 `0.0` 是算法策略的一部分；真实项目也可能改成返回 `std::optional<double>`。

## 延伸练习

- 新增一个 `std::vector<std::string>`，用投影函数返回字符串长度，观察同一算法如何复用。
- 故意让投影函数返回不能转换成 `double` 的类型，查看 concept 约束产生的编译错误。
- 把迭代器版本改写成 `template <std::ranges::range Range>`，比较调用点和约束表达的变化。
- 把空范围策略改成返回 `std::optional<double>`，思考泛型算法如何表达“没有结果”。
