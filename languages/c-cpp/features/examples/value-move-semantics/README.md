# 值语义与移动语义

## 目标

这个例子对应 C++ 的值语义和移动语义。目标是看懂对象在返回、传参、放入容器时到底是在复制内容，还是在转移资源。示例中的 `Buffer` 持有一个 `std::vector<int>`，并在构造、拷贝、移动时打印日志，学习者可以直接从输出判断每一步发生了什么。

值语义解决的真实工程问题是局部推理：一个对象被复制后，副本拥有自己的状态，调用方不必担心远处代码悄悄修改同一份数据。移动语义解决的问题是性能和所有权转交：字符串、向量、文件句柄这类对象可能持有堆内存或系统资源，如果只是把它交给容器或返回给调用者，深拷贝常常没有必要。

## 特性说明

`Buffer` 定义了拷贝构造、拷贝赋值、移动构造和移动赋值。拷贝会复制 `values_`，因此新旧对象互不影响；移动会把 `name_` 和 `values_` 从源对象转移到目标对象，源对象仍然处于可析构、可赋值的有效状态，但不应该再假设它保留原内容。`std::move(original)` 本身不移动数据，它只是把表达式转换成可以被移动构造接收的右值引用。

`make_buffer()` 展示“按值返回”并不必然昂贵。现代 C++ 编译器可以做返回值优化，也可以在必要时使用移动构造。`inspect_by_value(original)` 则故意按值传参，因此会从一个左值拷贝出函数参数。`std::vector<Buffer>` 展示容器持有值对象的方式：`push_back(std::move(original))` 转移已有对象，`emplace_back` 直接在容器内部构造新对象。

## 设计取舍

如果不用值语义，代码容易退化成到处传裸指针或共享可变对象。那样看似少了复制，却把生命周期和别名问题交给调用者：谁拥有数据、谁可以修改、对象什么时候失效，都需要额外约定。值语义让接口更像数学值，代价是大对象拷贝可能昂贵，所以 C++ 同时提供移动语义来表达“我不再需要这个源对象，可以把资源交出去”。

移动语义也不是越多越好。对小型平凡类型，拷贝可能和移动一样便宜；对仍要继续使用的对象，过早 `std::move` 会让后续代码难以读懂；对共享所有权，移动也不能替代清晰的所有权模型。这个例子里 `Buffer` 的移动构造标记为 `noexcept`，这是工程上很重要的细节：许多标准库容器在扩容时更愿意移动不会抛异常的元素，否则可能退回拷贝以保持异常安全。


## 观察点

- `copy` 表示创建了一份独立数据，修改其中一个不会影响另一个。
- `move` 表示资源所有权转移，常见于返回值、临时对象和 `std::move`。
- 容器扩容时可能移动已有元素；给 `std::vector` 预留容量可以减少这类搬迁。
- `inspect_by_value(original)` 会拷贝，因为 `original` 是仍然可用的左值。
- `push_back(std::move(original))` 之后不要再依赖 `original.name()` 的旧内容。

## 延伸练习

- 删除 `buffers.reserve(2)`，再多 `emplace_back` 几个元素，观察扩容时是否出现额外移动。
- 把 `inspect_by_value(Buffer buffer)` 改成 `inspect_by_ref(const Buffer& buffer)`，比较输出中拷贝日志的变化。
- 给 `Buffer` 增加一个 `append(int)` 方法，复制 `original` 后分别修改原对象和副本，验证值语义的独立性。
- 去掉移动构造函数上的 `noexcept`，观察不同编译器和标准库在容器扩容时可能选择拷贝还是移动。
