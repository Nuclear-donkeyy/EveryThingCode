# Typed Data Shapes

## 目标

把 TypeScript 的结构化类型思想翻译成可运行的 JavaScript：程序关心的是对象形状是否满足契约，而不是对象来自哪个类。示例同时强调运行时边界：从 JSON 得到的值必须先验证，再进入业务逻辑。

这个例子对应的语言特性和思想是 TypeScript 的结构化类型、类型收窄以及运行时输入边界。真实工程中，订单、用户、配置和 API 响应经常以普通对象形式流动；如果只靠注释或默认相信外部 JSON，代码会退化成到处写防御式判断，或者在很深的业务函数里才因为字段类型不对而崩溃。

## 特性说明

TypeScript 的结构化类型关注“值长什么样”，而不是“值从哪个类实例化出来”。如果一个对象有 `id: string` 和 `items: Item[]`，它就能满足订单接口的主要形状。这很贴合 JavaScript 的对象字面量风格，也方便渐进迁移老项目。

但 TypeScript 的类型只存在于开发期。`JSON.parse` 返回的值在运行时可能是数字、数组、缺字段对象或嵌套字段类型错误；即使你在 TS 里把它写成 `Order`，编译后也不会自动检查。示例中的 `isOrder` 就像真实项目里的类型守卫或 schema 校验：它把未知值收窄成可信订单，再交给 `summarizeOrder` 做业务计算。

## 设计取舍

结构化类型降低了协作成本：调用方不必继承某个基类，只要提供正确形状就能参与组合。代价是“形状相同”不一定代表“语义相同”，例如 `UserId` 和 `ProductId` 都是字符串时，结构化类型默认无法区分它们；真实项目可能需要 branded type、封装对象或更明确的领域模型。

运行时校验也有取舍。边界校验会多写一些代码，但它把不可信数据挡在入口处，让核心业务函数更干净。如果没有这个边界，`summarizeOrder` 里就要反复判断 `items` 是否存在、`quantity` 是否为数字，业务逻辑会被输入清洗细节淹没。

## 运行

```bash
node main.mjs
```

## 观察点

- `parseOrder` 先把 JSON 当作未知运行时值处理，没有假设它已经符合类型。
- `isOrder` 检查字段形状，对应 TypeScript 中 `Order` 接口会描述的结构。
- `summarizeOrder` 只接收验证后的订单对象，业务代码因此可以更直接。
- 修改第二条输入里的字段，例如把 `quantity` 改成字符串，可以观察边界校验如何阻止坏数据继续流动。
- 第三条输入会输出 `Invalid order shape`，验证了静态类型思想不能替代运行时检查。
- `priority` 是可选布尔字段，观察它缺失时为什么仍能通过形状检查，以及业务函数如何给出默认含义。

## 延伸练习

给订单增加 `customerEmail` 字段，并在 `isOrder` 中检查它必须包含 `@`。然后故意让一个输入缺少该字段，观察错误是在边界处暴露，而不是在摘要函数内部暴露。

再尝试把 `isOrder` 拆成 `isOrderItem` 和 `isOrder` 两个函数，体会运行时校验也需要可组合性。真实项目中可以把同样思想交给 Zod、Valibot、io-ts 或 JSON Schema，但先用标准库手写一遍，能看清 TypeScript 类型和运行时值之间的分工。
