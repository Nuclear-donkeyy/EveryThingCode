# JavaScript / TypeScript

## 语言定位

JavaScript / TypeScript 的第一版学习基线是 **Node.js 24.16.0 LTS**，工具链入口是 **Node.js 24.16.0**。它主要用于：Web 前端、Node 服务、全栈应用、工具链。

JavaScript 的核心定位是“运行在到处都有的宿主环境里的脚本语言”：浏览器、Node.js、边缘函数、桌面壳和构建工具都能运行它。它的设计哲学偏向快速表达、动态对象、函数一等公民和事件驱动 I/O；语言本身很小，但生态极大。TypeScript 则是在不改变运行时的前提下给 JavaScript 加上静态类型、编辑器推断和大项目可维护性。学习时要把二者合在一起看：JS 决定运行时行为，TS 决定开发期约束。

## 适合场景

- Web 前端和全栈项目：浏览器 API、React/Vue/Svelte、Node API、SSR/边缘渲染都围绕同一语言展开。
- I/O 密集型服务和工具链：HTTP 服务、CLI、构建器、代码生成器、脚本自动化都能借助事件循环快速落地。
- 需要高迭代速度和丰富生态的产品：npm 上的 SDK、UI 组件、测试工具、云服务客户端非常完整。
- 不太适合 CPU 长时间满载的单进程计算任务；需要 Worker、原生扩展、WASM 或拆到专门服务。
- 不太适合完全无纪律的大型代码库；动态特性很多，如果缺少 TypeScript、测试和边界约束，后期成本会迅速上升。

## 核心语法

重点学习变量/常量、函数、模块、数据结构、泛型或类型标注、控制流，以及该语言最常见的代码组织方式。案例会尽量保持短小，让语法特征直接暴露出来。

实际写法以 `const`、`let`、箭头函数、对象字面量、数组方法、解构、模板字符串和 ES Module 为基础。惯用代码通常把“数据转换”写成 `map`、`filter`、`reduce` 或清晰的 `for...of`，把“异步步骤”写成 `async/await`，把“可组合能力”写成小函数或对象方法。TS 中要优先用接口、类型别名、联合类型、泛型和字面量类型表达边界；运行时仍然是 JS，所以来自网络、文件、数据库的数据仍需显式校验，不能把类型标注当成输入验证。

## 类型/内存/并发模型

- 类型模型：JS 动态类型，TS 结构化静态类型。
- 并发模型：事件循环、Promise、async/await、Worker。
- 内存与资源：结合语言自己的生命周期管理方式学习，不把所有语言都套成同一种范式。

JS 的类型包含 `number`、`bigint`、`string`、`boolean`、`symbol`、`undefined`、`null` 和对象，数组、函数、日期、Map/Set 都是对象体系的一部分。TS 采用结构化类型：只要形状匹配就可赋值，这非常适合对象字面量和渐进迁移，但也要求理解类型收窄、可选属性、`unknown` 与 `any` 的差别。内存由垃圾回收管理，常见泄漏来自全局缓存、闭包持有大对象、事件监听未清理、定时器未取消。资源模型要主动处理文件句柄、网络连接、AbortSignal 和流的关闭。

并发上，主线程靠事件循环调度宏任务和微任务；Promise 不是线程，而是异步结果的表示。Node 适合大量等待 I/O 的工作，CPU 密集任务应交给 Worker Threads、子进程或外部服务。浏览器中还要区分主线程、Web Worker、Service Worker 与渲染时机，避免把重活塞进交互线程。

## 标准库与包管理

包管理入口：npm / pnpm / yarn。第一版案例优先使用标准库，只有框架章节才引入生态依赖。

Node 标准库覆盖文件系统、路径、URL、HTTP、加密、流、测试、进程和事件。现代 Node 已内置 `fetch`、Web Streams 和测试运行器，很多小脚本不必马上引入依赖。包管理要理解 `package.json`、锁文件、语义化版本、ESM/CJS 差异、脚本命令和依赖类型。npm 是默认入口，pnpm 更重视磁盘复用和严格依赖，yarn 常见于既有项目。选工具时优先尊重项目现状，而不是混用锁文件。

## 错误处理

Error 对象、Promise rejection、Result 风格封装。学习时关注错误如何被表达、传播、恢复，以及如何避免把异常路径藏在业务逻辑里。

同步代码用 `throw`/`try...catch...finally`，异步代码要 `await` 后捕获或在调用边界统一处理。未处理的 Promise rejection、吞掉异常的空 `catch`、只抛字符串而不是 `Error`，都会让定位变困难。业务错误适合用带 `code`、`cause`、上下文信息的自定义错误；可预期失败也可以返回 `Result` 风格对象，让调用方显式分支。资源清理要放在 `finally`、AbortSignal 回调或框架生命周期里。

## 工程化

第一阶段关注代码格式、测试入口、依赖声明和可重复运行。大型工程主题，如性能分析、发布、观测和安全，会在框架章节逐步展开。

一个健康项目通常包含 TypeScript 配置、格式化、lint、测试、构建、运行脚本和锁文件。常见组合是 `tsconfig.json`、ESLint、Prettier、Vitest/Jest/Node test runner、tsx/ts-node、Vite 或 bundler。工程化重点不是堆工具，而是让“安装、运行、测试、构建、发布”可重复。库项目要关心导出入口、类型声明、ESM/CJS 兼容和树摇；应用项目要关心环境变量、配置分层、日志、错误边界和部署产物。

## 常见坑

- 只学习语法而忽略包管理和项目结构。
- 把其他语言的范式硬搬过来，错过本语言的惯用表达。
- 示例能跑但没有预期输出，导致无法判断自己是否真正理解。
- 混淆 `null`、`undefined`、空字符串和空数组，导致边界判断不一致。
- 误解 `this`、闭包、原型链和模块作用域，在回调或类方法中丢失上下文。
- 认为 TypeScript 能保护所有运行时输入，忽略 JSON、表单和环境变量校验。
- 滥用 `any`、过度复杂的类型体操，或为了类型漂亮牺牲可读代码。
- 忘记异步错误传播：没有 `await`、没有返回 Promise、并发任务没有统一收敛。
